# 메모리 레이아웃 & 정적 할당 규율 — 풋프린트

> 학습 자료(공용 · 난이도 낮음). 펌웨어가 512KB 플래시·128KB SRAM 안에 어떻게 담기는가,
> 왜 malloc을 금지하는가, `.map`을 어떻게 읽는가. **무-malloc 정적 규율은 결정론적 펌웨어의 이력서 한 줄.**
> 선행: [stm32-basics.md](stm32-basics.md) §2(부팅), [freertos-concepts.md](freertos-concepts.md) §7(힙).

---

## 1. 두 개의 메모리 — 플래시 vs SRAM

| | 플래시(Flash) | SRAM |
|---|---|---|
| 크기(F411) | 512KB | 128KB |
| 성격 | 비휘발성(전원 꺼도 유지), 느림(wait-state) | 휘발성, 빠름 |
| 담는 것 | 코드(.text), 상수(.rodata), .data 초기값 | 실행 중 변수(.data/.bss), 스택, 힙 |

부팅 시 스타트업 코드가 **플래시의 .data 초기값을 SRAM으로 복사**하고 **.bss를 0으로** 채운다
([stm32-basics.md](stm32-basics.md) §2의 "리셋 핸들러가 전역변수 초기화"가 이것).

> CS 연결: 컴퓨터구조/시스템의 **프로그램 메모리 레이아웃**(text/data/bss/heap/stack) 그대로.
> 데스크톱과 다른 점은 코드가 RAM이 아니라 **플래시에서 직접 실행(XIP)**된다는 것.

---

## 2. 섹션(section) — 뭐가 어디에 사는가

- **.text**: 코드. 플래시.
- **.rodata**: const/문자열/**`model_weights.h`의 가중치 배열**(const면). 플래시. → int8이 4배 작은 게 여기서 결정적.
- **.data**: 초기값 있는 전역/정적 변수. 플래시에 초기값, 실행 시 SRAM에 상주.
- **.bss**: 0으로 시작하는 전역/정적(예: 큰 정적 버퍼, **아레나**). SRAM. 플래시 안 먹음.
- **stack**: 함수 호출·지역변수. SRAM 위쪽에서 아래로 자람. FreeRTOS는 **태스크마다 별도 스택**.
- **heap**: malloc용. **이 프로젝트는 안 씀**(§4).

---

## 3. `.map` 파일 읽기 — 풋프린트의 근거

빌드하면 링커가 `.map`을 뱉는다(그리고 콘솔에 text/data/bss 요약). 여기서:

- **Flash 사용** ≈ text + rodata + data(초기값). 512KB 대비 얼마인가.
- **SRAM 사용** ≈ data + bss + (스택들 + FreeRTOS 힙). 128KB 대비 얼마인가.
- 어떤 심볼이 큰지(가중치 배열, 아레나, 버퍼)를 `.map`에서 찾아 `docs/memory_footprint.md`에 표로.

> 이게 PLAN.md의 "flash/RAM/아레나 사용량 기록" DoD. **측정 산출물의 일부**다.

## 4. 왜 malloc 금지인가 — 결정성

CLAUDE.md 규칙: **펌웨어에서 malloc 금지, 정적 버퍼 + 아레나만.** 이유:

- **단편화(fragmentation)**: 오래 도는 임베디드에서 malloc/free를 반복하면 힙이 조각나 어느 순간
  "메모리는 남는데 큰 블록을 못 잡음" → 예측 불가한 실패. 실시간 결정성과 상극.
- **비결정적 시간**: malloc 자체의 소요 시간이 힙 상태에 따라 변함 → WCET 산정 불가.
- **정적 아레나**: 큰 `static uint8_t arena[N];`(=.bss)를 미리 잡고 그 안에서만 배분. 크기가
  **컴파일 타임에 확정**되고, 넘치면 링크/부팅에서 바로 드러난다.

> 스토리지/메모리 컨트롤러 펌웨어가 정확히 이 규율(정적 할당, 결정론적 시간)로 짜인다.
> "무-malloc 정적 아레나 + WCET 고려"는 그 세계의 기본기 → 이력서 한 줄의 근거.

## 5. FreeRTOS 힙 & 스택 — 애매한 지점 정리

- `xTaskCreate`/`osThreadNew`는 내부적으로 **FreeRTOS 힙(heap_4)**에서 TCB·스택을 잡는다.
  이건 libc malloc이 아니라 **커널이 관리하는 고정 크기 정적 배열**이다([freertos-concepts.md](freertos-concepts.md) §7).
- 규율: **모든 태스크/큐를 `main()`에서 스케줄러 시작 전에만 생성**, 런타임 생성/삭제 금지 →
  사실상 정적. 더 엄격히는 `xTaskCreateStatic`으로 버퍼를 직접 준다.
- **스택 크기 산정**: 태스크마다 얼마나 줄지가 문제. `uxTaskGetStackHighWaterMark`로 **실사용
  최고치**를 재서(측정!) 여유를 두고 확정. printf·큰 지역배열이 스택을 크게 먹으니 주의.
- **스택 오버플로**: 넘으면 조용히 옆 메모리를 밟아 "엉뚱한 변수가 깨짐". `configCHECK_FOR_STACK_OVERFLOW`
  훅을 켜서 잡는다(W2).

## 6. 아레나 산정 — 추론 버퍼

- int8 모델의 중간 활성값·입력 윈도우·(오토인코더면) 재구성 버퍼를 담을 **정적 아레나** 하나를 잡는다.
- 크기는 모델 구조에서 계산(레이어별 최대 활성 크기의 합 또는 재사용 스킴). 넉넉히 잡고 `.map`으로 확인.
- TFLite Micro의 "텐서 아레나"와 같은 철학이지만, 여기선 **직접 짠 커널이라 우리가 크기를 통제**한다.
