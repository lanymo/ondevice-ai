## 1. 전원과 GND — 소프트웨어 이전의 진짜 1층

### 왜 CS 전공자가 여기서 막히나

PC/서버 프로그래밍에선 "전기"를 생각할 일이 없다. 임베디드에선 이 가정이 깨진다.
**코드가 완벽해도 전압·GND가 틀리면 아무것도 안 돌고, 증상은 소프트웨어 버그처럼 보인다.**
이 절의 목적은 "소프트웨어로 보이지만 사실 전기 문제"인 현상을 알아보는 눈.

### 전압 도메인 — 3.3V와 5V가 공존한다

| 전압 | 어디서 | 무엇에 |
|---|---|---|
| 5V | Nucleo 5V 핀 또는 USB | HC-SR04 로직 전원 (채택 시) |
| 3.3V | STM32 내부 레귤레이터 | MCU 코어, MPU6050 로직 |

핵심: **STM32 핀은 3.3V 로직이다.** 5V 신호를 3.3V 입력 핀에 직접 넣으면 핀이 상할 수
있다. HC-SR04의 Echo 출력(5V)이 대표 사례 — 분압 저항 필요 (parts-guide.md §3).
반대로 3.3V 출력을 5V 입력이 읽는 건 대개 문제없다.

### 공통 GND — 가장 많이 데이는 곳

GND = 모든 전압을 재는 **0V 기준선**.

> 전압은 절대값이 아니라 "두 점 사이의 차이"다. "이 신호가 3.3V다" = "GND보다 3.3V
> 높다". MCU의 GND와 센서의 GND가 연결돼 있지 않으면 기준이 서로 달라 신호 해석이
> 무의미해진다.

비유: 두 사람이 "해발 100m"를 말하는데 각자 다른 바다를 기준으로 삼으면 비교 불가.
**VCC는 각자 맞는 전압으로 가더라도, GND는 반드시 전부 하나로 묶는다.**
센서 하나의 GND를 빠뜨리면 그 센서만 값이 미쳐 날뛴다 — 코드는 멀쩡한데.

## 3. I2C — 두 선으로 여러 칩과 대화하는 버스 (MPU6050)

> 실제 브링업을 겪은 뒤의 정리는 [qna-core.md](qna-core.md) Q7~Q12가 더 구체적이다.
> 이 절은 개념 뼈대만.

- **SDA**(데이터) + **SCL**(클럭) 두 선을 여러 부품이 공유하는 버스. 마스터(STM32)가
  클럭을 만들고, 매 통신을 "주소 부르기"로 시작해 그 주소의 슬레이브만 응답한다.
  UART와 달리 클럭 선이 있어 속도 불일치 문제가 없다.
- CS 비유: 공유 버스 위의 마스터-슬레이브 프로토콜. 주소는 네트워크의 MAC 주소 격 —
  작은 보드 내부의 버스형 LAN.
- **주소**: MPU6050은 AD0 핀 전압으로 0x68/0x69 중 하나 — 같은 부품 2개를 한 버스에
  붙이기 위한 장치 (qna-core.md Q8).
- **풀업 저항**: I2C 선은 오픈 드레인이라 부품들은 선을 끌어내릴 수만 있다. 아무도 안
  끌어내릴 때 3.3V로 되돌릴 풀업이 버스에 필수. GY-521은 모듈에 내장 (qna-core.md Q7).
- **통신 = 원격 레지스터 읽기/쓰기**: stm32-basics의 "주변장치 = 메모리 매핑 레지스터"
  멘탈 모델이 센서 안에서도 성립한다. WHO_AM_I 확인 → sleep 해제 → 데이터 레지스터
  주기 읽기 순서의 이유는 qna-core.md Q10~Q12.
- 삽질 순서 (실증됨): 응답 없음 → ① 주소(0x68/0x69, HAL `<<1`) ② 풀업 ③ SDA/SCL 스왑,
  GND 공통.

## 4. 타이머 인풋캡처 — 시간을 재서 거리를 안다 (HC-SR04, 조건부)

### HC-SR04가 거리를 알려주는 방식

1. MCU가 Trig 핀에 짧은 펄스(약 10µs) = "지금 쏴".
2. 센서가 초음파를 발사하고 **Echo 핀을 HIGH로 올린다**.
3. 메아리가 돌아오면 **Echo를 다시 LOW로 내린다**.
4. **Echo가 HIGH였던 시간 = 소리 왕복 시간**. 음속 곱하고 2로 나누면 거리.
   대략 왕복 58µs가 1cm (음속 340m/s 기준).

핵심은 "Echo 펄스 폭"이라는 시간을 정확히 재는 것.

### 왜 소프트웨어로 재면 안 되나

```c
while (Echo == LOW);   // 올라갈 때까지 대기
t0 = now();
while (Echo == HIGH);  // 내려갈 때까지 대기
pulse = now() - t0;
```

① busy-wait 동안 CPU가 다른 일을 전혀 못 하고, ② 마이크로초를 소프트웨어 루프로 재면
인터럽트 때문에 부정확하며, ③ FreeRTOS에서 다른 태스크가 끼어들면 측정이 밀린다.

**타이머 인풋캡처**가 하드웨어로 해결한다:

> 타이머는 계속 카운터를 세고 있다. 인풋캡처 모드로 설정하면 지정한 핀의 **에지(신호가
> 바뀌는 순간)에 그 순간의 카운터 값을 자동으로 latch한다.** CPU는 관여하지 않는다.

Echo 상승 에지에 캡처(t0), 하강 에지에 캡처(t1), 차가 펄스 폭. CPU는 하강 에지
인터럽트에서 "저장된 두 값의 차 읽기"만 한다 — freertos-concepts §4의 deferred
interrupt 패턴 그대로: ISR은 캡처값만 큐에 넣고, 계산은 태스크가.

### 타이머 클럭 = 자 눈금

카운터 "1 증가"가 실제 몇 ns인지는 타이머 클럭과 분주 설정으로 정해진다. 이 계산을
틀리면 거리가 통째로 어긋난다. 측정 주기는 60ms 이상 확보(이전 반향 혼입 방지).

## 5. FreeRTOS와의 연결 — 이 부품들이 태스크가 되는 방식

| 태스크 | 이 문서의 무엇 | 통신 | 특징 |
|---|---|---|---|
| sensor | MPU6050 읽기(§3) | I2C | 100Hz 주기, 값을 큐로 |
| action (로컬 액션) | 마감시한 이벤트 → LED/부저 | 타이머 ISR(기본), HC-SR04 인풋캡처(§4, 스트레치) | 낮은 지연이 마감시한 목표 |
| inference | IMU 윈도우 → int8 추론 | 큐 | 무거운 payload, 우선순위 가변(축 A 실험 변수) |
| logger | UART(stm32-basics) | UART | 최하 우선순위, printf 전용 |

층 구조: **전기(§1) → 주변장치 프로토콜(§3~4, GPIO/UART) → 태스크 스케줄링(freertos)
→ 그 위의 AI 추론(W3~4)**. W2는 아래 두 층을 실물로 세우는 주간이다.

## 6. W2 삽질 플레이북 (증상 → 의심 순서)

| 증상 | 1순위 의심 | 2순위 | 3순위 |
|---|---|---|---|
| I2C 응답 없음(WHO_AM_I 안 읽힘) | 주소(0x68/0x69, HAL `<<1`) | 풀업 저항 | SDA/SCL 스왑, GND 공통 |
| I2C는 되는데 가속도 0 고정 | **sleep 미해제** (qna-core.md Q11) | — | — |
| 초음파 값이 튐 | 타이머 클럭 계산(§4) | 측정 주기 <60ms | Echo 전압 레벨(5V?) |
| 센서 하나만 값이 미침 | 그 센서 GND 누락(§1) | VCC 전압 틀림 | 배선 접촉 불량 |
| 전부 이상하게 동작 | 공통 GND(§1) | 전원 용량 부족 | — |

> 규칙: 임베디드에서 "코드가 이상하다"는 결론은 **전원·GND·배선을 배제한 뒤에만** 내린다.
