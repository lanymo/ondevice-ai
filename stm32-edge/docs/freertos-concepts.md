# FreeRTOS 개념 노트 — 임베디드 초심자용 (CS 전공자 기준)

> W1 학습 자료. OS 수업에서 배운 개념(스레드, 스케줄러, 뮤텍스)을 이미 안다고 가정하고,
> "리눅스와 뭐가 다른가"를 축으로 설명한다. 마지막 절에서 이 프로젝트(W2 태스크 골격,
> W4 지터 실험)와 직접 연결한다.

---

## 1. 왜 RTOS인가 — "Real-Time"은 빠르다는 뜻이 아니다

베어메탈 펌웨어의 기본 구조는 수퍼루프다:

```c
while (1) {
    read_sensors();
    compute_control();
    drive_motors();
    log_uart();
}
```

이 구조의 문제: `log_uart()`가 어쩌다 5ms 걸리면 그 주기의 제어 계산이 5ms 늦는다.
기능이 늘수록 "한 바퀴 도는 시간"이 들쭉날쭉해지고, 제어 주기가 흔들린다.

RTOS가 파는 것은 **속도가 아니라 결정성(determinism)**이다.
"모터 제어는 다른 일이 뭘 하고 있든 10ms마다 반드시 실행된다"를 보장하는 게 목적.
평균이 빠른 것(리눅스가 잘하는 것)과 최악의 경우가 예측 가능한 것(RTOS가 잘하는 것)은
다른 성질이다. 이 프로젝트의 축 A 실험이 정확히 이걸 측정한다 — 추론이라는 무거운 작업을
추가했을 때 마감시한 이벤트→로컬 액션 지연의 p99가 어떻게 변하는가.

FreeRTOS는 커널 하나가 전부다. 프로세스도, 가상 메모리도, 파일시스템도, 사용자/커널
모드 분리도 없다. 커널이 우리 코드와 같은 주소 공간에 링크되는 라이브러리이고,
전체가 하나의 펌웨어 바이너리다.

## 2. 태스크 — pthread와 비슷하지만 다른 점이 핵심

FreeRTOS의 실행 단위는 태스크(task)다. pthread와의 대응:

| | pthread (리눅스) | FreeRTOS 태스크 |
|---|---|---|
| 주소 공간 | 프로세스별 가상 메모리 | 전부 공유 (MMU 없음, 물리 주소 그대로) |
| 스택 | OS가 자동 확장 | **생성 시 고정 크기 지정, 넘치면 그냥 망가짐** |
| 스케줄링 | CFS (공정성 지향) | 고정 우선순위 선점형 (공정성 개념 없음) |
| 개수 | 수천 개도 가능 | 보통 3~10개 (RAM 128KB 안에서) |

임베디드 초심자가 가장 많이 당하는 게 **스택 오버플로**다. 태스크마다 스택을
몇 백 워드 단위로 미리 떼어주는데, 그 태스크 안에서 큰 지역 배열을 잡거나
printf(내부적으로 스택을 많이 씀)를 부르면 조용히 옆 메모리를 밟는다.
증상은 "전혀 관련 없어 보이는 변수가 이상한 값이 됨" — 디버깅 난이도 최악.
`configCHECK_FOR_STACK_OVERFLOW` 옵션을 켜두면 훅으로 잡아준다 (W2에서 켤 것).

태스크의 전형적인 모습은 "무한 루프 + 블로킹 대기"다:

```c
void sensor_task(void *arg) {
    for (;;) {
        // 여기서 블로킹: 큐 대기, 딜레이 등. CPU를 놓아준다.
        vTaskDelay(pdMS_TO_TICKS(10));
        read_imu(&sample);
        xQueueSend(imu_queue, &sample, 0);
    }
}
```

블로킹 함수를 호출하지 않고 계속 도는 태스크는 자기보다 낮은 우선순위를 영원히
굶긴다(리눅스처럼 타임슬라이스로 공평하게 나눠주지 않는다). "태스크는 반드시
어딘가에서 블로킹한다"가 기본 규율이다.

## 3. 스케줄러 — 규칙이 단순해서 오히려 예측 가능하다

규칙은 딱 하나: **실행 가능한(Ready) 태스크 중 우선순위가 가장 높은 놈이 항상 CPU를
가진다.** 더 높은 우선순위 태스크가 Ready가 되는 순간 즉시 선점한다.

- 숫자가 클수록 높은 우선순위 (리눅스 nice와 반대 방향이니 주의).
- 같은 우선순위끼리는 틱(tick)마다 라운드로빈.
- 틱: 주기적 타이머 인터럽트 (기본 1kHz = 1ms). 시간 관련 API의 해상도가 이걸로 결정된다.
- 아무도 실행할 게 없으면 유휴(Idle) 태스크가 돈다 (우선순위 0, 커널이 자동 생성).

주기적 실행에는 두 API가 있는데 **차이가 이 프로젝트에서 중요하다**:

- `vTaskDelay(10)` — "지금부터 10틱 쉬어라". 루프 본문 실행 시간만큼 주기가 밀린다.
  주기가 10ms + 본문 시간이 되어 드리프트한다.
- `vTaskDelayUntil(&last_wake, 10)` — "지난 기상 시각 + 10틱에 깨워라". 본문 실행
  시간과 무관하게 절대 주기를 유지한다. **제어 루프와 100Hz IMU 샘플링은 반드시 이걸 쓴다.**
  W4에서 측정하는 "제어 주기 지터"는 vTaskDelayUntil로 잡은 주기가 실제로 얼마나
  흔들리는가다.

## 4. 인터럽트(ISR)와 태스크 — 두 개의 세계

리눅스 앱 개발에선 인터럽트를 직접 만질 일이 없지만, 임베디드에선 코드의 절반이
ISR(Interrupt Service Routine)과 얽힌다. 규칙:

1. ISR은 모든 태스크보다 우선한다. 스케줄러도 ISR을 선점할 수 없다.
2. ISR 안에서는 블로킹 금지, 오래 걸리는 일 금지. "값 받아서 큐에 넣고 즉시 리턴"이 전부.
3. ISR 안에서는 전용 API를 쓴다: `xQueueSendFromISR()`처럼 `FromISR` 접미사가 붙은 것만.
   일반 버전을 ISR에서 부르면 크래시하거나 미묘하게 오동작한다.

전형적인 협업 패턴 — **지연 처리(deferred interrupt handling)**:

```
[UART 수신 ISR]  바이트를 큐에 넣음 (수 마이크로초)
      ↓ 큐
[UART 태스크]    큐에서 꺼내 파싱/로깅 (느긋하게, 태스크 우선순위로)
```

무거운 일은 태스크로 미루고 ISR은 최단시간에 끝낸다. HC-SR04 에코 폭 측정(타이머
인풋캡처 인터럽트), MPU6050 데이터 수신이 다 이 패턴을 탄다.

## 5. 큐 — 태스크 간 통신의 기본 수단

FreeRTOS 큐는 고정 크기 아이템의 링버퍼 + 블로킹 대기가 합쳐진 것. CS 수업의
bounded buffer (생산자-소비자) 문제의 커널 구현체다.

```c
QueueHandle_t q = xQueueCreate(16, sizeof(imu_sample_t)); // 16개짜리
xQueueSend(q, &sample, 0);              // 0 = 가득 차면 기다리지 않고 실패
xQueueReceive(q, &out, portMAX_DELAY);  // 올 때까지 블로킹
```

주의할 특성:

- **값 복사다.** 포인터가 아니라 구조체 내용이 큐 내부 버퍼로 복사된다. 지역변수를
  넣고 리턴해도 안전하다는 뜻. (큰 데이터면 포인터를 담되, 소유권 규칙을 정해야 한다.)
- 받는 쪽이 `portMAX_DELAY`로 대기하면 그 태스크는 Blocked 상태가 되어 CPU를 전혀
  안 쓴다. 데이터가 도착하는 순간 Ready로 깨어난다. 폴링 루프가 필요 없다.
- 공유 전역변수 + 플래그로 통신하고 싶은 유혹이 들 텐데, 큐가 동기화 문제를
  이미 다 풀어놓은 물건이다. 기본은 큐.

## 6. 세마포어와 뮤텍스 — 비슷해 보이지만 용도가 다르다

- **바이너리 세마포어**: "이벤트 알림"용. 주로 ISR → 태스크 시그널링.
  ISR이 `xSemaphoreGiveFromISR()`, 태스크가 `xSemaphoreTake(sem, portMAX_DELAY)`로
  잠들어 있다가 깨어난다. 데이터 없이 "일어나!"만 전달할 때 큐보다 가볍다.
- **뮤텍스**: "공유 자원 보호"용. 예: 여러 태스크가 같은 UART로 출력할 때.

왜 구분하나? 뮤텍스에만 **우선순위 상속(priority inheritance)**이 붙기 때문이다.
OS 수업의 우선순위 역전(priority inversion) 문제 그대로다: 낮은 태스크 L이 뮤텍스를
쥔 채로, 높은 태스크 H가 그 뮤텍스를 기다리는데, 중간 태스크 M이 L을 선점해버리면
H가 M 때문에 무한정 기다린다. 뮤텍스는 이때 L의 우선순위를 H 수준으로 잠깐 끌어올려
문제를 푼다. 세마포어는 이 기능이 없으므로 자원 보호에 쓰면 안 된다.

이 프로젝트에서는 우선순위 역전이 남 얘기가 아니다 — UART 로깅 뮤텍스를 제어 태스크와
로깅 태스크가 공유하면 W4 지터 측정에 그대로 나타날 수 있다.

## 7. 메모리 — 이 프로젝트의 규칙과 FreeRTOS의 힙

CLAUDE.md 규칙: **펌웨어에서 malloc 금지, 정적 버퍼 + 아레나만.** 그런데 FreeRTOS의
`xTaskCreate()`, `xQueueCreate()`는 내부적으로 FreeRTOS 자체 힙(`pvPortMalloc`)에서
TCB와 스택을 할당한다. 정리하면:

- FreeRTOS 힙은 libc malloc이 아니라 커널이 관리하는 고정 크기 정적 배열이다
  (CubeMX 기본은 heap_4: 정적 배열 안에서 병합 가능한 할당자).
- **초기화 시점에만** 태스크/큐를 생성하고 런타임 중에는 생성/삭제하지 않으면,
  사실상 정적 할당과 동일한 결정성을 가진다. 이 프로젝트는 이 원칙으로 간다:
  모든 커널 객체는 `main()`에서 스케줄러 시작 전에 생성, 이후 생성/삭제 금지.
- 더 엄격하게 가려면 `xTaskCreateStatic()`으로 버퍼를 직접 주는 방법도 있다
  (필요해지면 그때 전환).
- W3의 int8 모델 "아레나"도 같은 철학이다: 큰 정적 배열 하나를 미리 잡고
  그 안에서만 쓴다. (PLAN 2026-07-24 변경으로 TFLite Micro 통합은 폐기되고
  직접 짠 int8 커널로 대체됐지만, 아레나 개념은 그대로 간다.)

## 8. printf와 newlib 재진입 — 로깅 창구는 반드시 하나

> W2에서 실제로 내린 결정. 태스크를 추가할 때마다 다시 걸리는 함정이라 여기 남긴다.

**문제**: `printf`, `malloc`, `strtok`, `errno` 같은 newlib 함수들은 전역 포인터
`_impure_ptr`이 가리키는 **하나의 상태 구조체**(`struct _reent`)를 공유한다. 출력 버퍼
위치, 진행 중인 파싱 상태 등이 거기 들어 있다.

싱글 스레드에선 문제가 없지만 FreeRTOS는 **선점형**이다:

```
태스크 A: printf("cycles=%lu\r\n", n)  실행 중 ─┐ (버퍼에 쓰는 중간)
                                                │ ← 여기서 선점당함
태스크 B: printf("latency=%lu\r\n", m)  ────────┘ 같은 버퍼를 덮어씀
```

결과는 출력이 뒤섞이거나 깨지는 것이고, 타이밍에 의존해서 **재현이 안 되는** 종류의
버그가 된다.

**해법은 두 가지**:

1. `USE_NEWLIB_REENTRANT = Enabled` — FreeRTOS가 태스크마다 `_reent`를 따로 주고
   컨텍스트 스위치 때 `_impure_ptr`을 바꿔치기한다. 안전하지만 **태스크 수 × 수백 바이트
   RAM**을 먹는다.
2. **호출자를 하나로 제한** — 애초에 경쟁이 생기지 않게 한다.

**이 프로젝트는 2번을 택했다.** 이유는 RAM 절약(W4 `memory_footprint.md` 서사)이기도
하지만, 더 중요하게는 **측정 요구와 결론이 같기 때문**이다. 115200bps에서 한 글자에
약 87µs가 걸리므로 `printf`는 어차피 측정 경로 밖으로 빼야 한다(§측정 방법론의 함정 2번).
"로깅은 최하 우선순위 태스크 하나가 전담한다"는 구조가 재진입 문제와 측정 오염 문제를
동시에 푼다.

**지켜야 할 규칙**:

- 스케줄러 기동 후 `printf`(및 newlib 함수)는 **logger 태스크에서만** 호출한다.
- 다른 태스크는 숫자를 **큐에 넣고** 즉시 자기 일로 돌아간다(§5 큐).
- **ISR에서는 절대 금지** — 재진입에 더해 블로킹이라 인터럽트를 수십~수백 µs 잡는다(§11의 2).
- 파일이나 USER CODE 블록의 위치는 무관하다. 기준은 **런타임에 어느 태스크의 실행
  흐름에서 불리느냐**다.
- `osKernelStart()` **이전**의 `main()` 안에서는 안전하다 — 실행 흐름이 하나뿐이라
  경쟁 자체가 성립하지 않는다. W2의 부팅 배너가 여기 해당한다.

**곁다리 — `printf`의 숨은 malloc**: newlib은 첫 stdio 호출 때 출력 버퍼를 `malloc`으로
잡는다. §7의 malloc 금지 규칙과 정면으로 부딪히므로, `main()`에서 첫 출력 **전에**
`setvbuf(stdout, NULL, _IONBF, 0)`로 버퍼링을 꺼서 할당 자체를 막는다.

## 9. CubeIDE에서 만나는 얼굴 — CMSIS-RTOS v2 래퍼

CubeMX로 FreeRTOS를 활성화하면 생성되는 코드는 `xTaskCreate`가 아니라
`osThreadNew`, `osMessageQueueGet` 같은 함수를 쓴다. 이건 ARM의 표준 래퍼
**CMSIS-RTOS v2** API로, 밑에서 FreeRTOS를 호출하는 껍데기다.

- 대응 관계: `osThreadNew` ≈ `xTaskCreate`, `osMessageQueue*` ≈ 큐,
  `osSemaphore*` / `osMutex*` ≈ 세마포어/뮤텍스, `osDelay` ≈ `vTaskDelay`.
- 우선순위 상수도 다르다: `osPriorityNormal`, `osPriorityHigh` 등 (내부에서
  FreeRTOS 숫자로 매핑됨).
- 인터넷 자료는 FreeRTOS 네이티브 API 기준이 많아서 둘을 오가며 읽게 된다.
  개념은 동일하니 이름 매핑만 익히면 된다. 이 프로젝트는 CubeMX가 생성해주는
  CMSIS-RTOS v2를 그대로 쓰되, 래퍼에 없는 기능(`vTaskDelayUntil` 등)은
  네이티브 API를 섞어 쓴다.

## 10. 이 프로젝트에 적용 — 태스크 골격과 축 A 실험

태스크 분리는 대략 이런 그림이 된다 (핀맵/우선순위 확정 전, 개념 스케치):

| 태스크 | 주기 | 우선순위(상대) | 역할 |
|---|---|---|---|
| sensor (IMU) | 10ms (100Hz, vTaskDelayUntil) | 상 | MPU6050 읽기 → 큐로 전달 |
| inference | 이벤트 (큐 대기) | **가변 ← 축 A 실험 변수** | IMU 윈도우 모아 int8 모델 추론 (무거운 payload) |
| action (로컬 액션) | 이벤트 (마감시한) | 마감시한 준수 목표 | 타이머 ISR 이벤트 → LED/부저 등 로컬 액션 |
| logger | 이벤트 (큐 대기) | 최하 | UART로 측정치/로그 출력 |

축 A 실험이 무엇인지 이 문서의 언어로 다시 쓰면:

> inference 태스크의 우선순위를 action보다 높게/낮게(또는 추론을 청킹) 바꿔가며,
> "마감시한 이벤트 → action 응답"까지의 지연이 얼마나 흔들리는지(p50/p99/max)를
> 타이머 타임스탬프로 측정한다. 추론(수 ms짜리 CPU 연산)이 높은 우선순위·비청킹이면
> action을 오래 막아 지연 꼬리가 커지고, 낮추거나 청킹하면 마감시한 이벤트가 끼어들
> 틈이 생겨 지연이 보존된다 — 를 수치로 증명하는 것.

즉 이 문서의 개념 중 **선점형 고정 우선순위 스케줄링 + 우선순위 역전 + 선점 지점(청킹)**이
축 A 그래프 한 장에 전부 들어간다. (이론적 배경은 [realtime-scheduling.md](realtime-scheduling.md).)

## 11. 초심자 함정 요약 (당하기 전에 읽기)

1. 스택 오버플로 — 태스크 스택은 고정 크기. 큰 지역 배열, printf 주의. 오버플로 체크 훅 켜기.
2. ISR에서 일반 API 호출 — `FromISR` 버전만. ISR에서 printf 금지.
2-1. **여러 태스크에서 printf** — `USE_NEWLIB_REENTRANT`를 끈 상태라 출력이 조용히 깨진다.
   logger 태스크 하나만 창구로 쓴다 (§8).
3. 블로킹 없는 무한 루프 태스크 — 낮은 우선순위 전부 굶는다.
4. `vTaskDelay`로 만든 "주기" — 드리프트한다. 주기 작업은 `vTaskDelayUntil`.
5. 세마포어로 자원 보호 — 우선순위 상속이 없다. 자원 보호는 뮤텍스.
6. 우선순위를 습관적으로 다 높게 — 전부 높으면 아무도 높지 않다. 기본은 낮게, 근거 있을 때만 올린다.
7. 스케줄러 시작(`osKernelStart`) 이후 코드 — `main()`에서 그 아래 줄은 실행되지 않는다 (정상).
