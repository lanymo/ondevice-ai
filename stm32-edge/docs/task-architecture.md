# 태스크 구조 — 5태스크 + 마감시한 이벤트 경로 + 추론 경로

> 구현: [Core/Src/app_tasks.c](../firmware/Core/Src/app_tasks.c) · [Core/Inc/app_tasks.h](../firmware/Core/Inc/app_tasks.h)
> 선행 개념: freertos-concepts.md, [measurement-methodology.md](measurement-methodology.md)
>
> W2 DoD: "추론 없이 **마감시한 이벤트 → 로컬 액션 지연**이 UART로 찍힘 + IMU 100Hz 스트림".
> 이 문서는 그 구조와, 보드에서 무엇을 확인해야 하는지를 적는다.
>
> **W3 변경 (2026-08-08)**: 추론 스텁이 **둘로 쪼개졌다** — 진짜 int8 추론 태스크(`infer`)와
> 축 A 스케줄링 실험용 합성 부하 태스크(`load`). 이유는 [system-design.md §1-8](system-design.md):
> 진짜 추론은 CPU의 0.2%라 스케줄링 실험의 독립변수가 될 수 없었다. 두 개를 한 태스크로
> 두면 "추론이 무거워서 액션이 밀렸다"는 **거짓 서사**가 만들어진다.

## 1. 태스크 5개와 우선순위

| 태스크 | 우선순위 | 스택(워드) | 주기/트리거 | 하는 일 |
|---|---|---|---|---|
| `action` | **48** | 256 | TIM2 이벤트 (50ms) | 지연 측정 + LD2 토글 = **로컬 액션** |
| `sensor` | 40 | 384 | 10ms (`vTaskDelayUntil`) | MPU6050 6축 폴링 100Hz + 주기 측정 + 윈도우 스냅숏 |
| `log` | 16 | 512 | 큐 수신 | printf/CSV 출력 **전담** |
| `infer` | **12** | 320 | 윈도우 완성 알림 (0.64s) | **진짜 int8 추론** → 이상 판정 → 로컬 액션 |
| `load` | 8 또는 **50** | 192 | 53ms마다 20ms 잡 | **합성 부하** (추론 아님). 축 A 스윕의 조작 대상 |

우선순위 숫자가 클수록 높다(`configMAX_PRIORITIES=56`). 배치의 근거:

- **action이 최상위**: 하드 마감시한을 가진 유일한 태스크. 다른 무엇도 이걸 밀어내면 안 된다.
- **log가 infer보다 위**: UART 출력이 추론에 막혀 밀리면 측정 보고가 실시간성을 잃는다.
  대신 action/sensor보다는 아래 — printf가 마감시한 경로를 절대 물지 않게.
  이 결정의 **실제 비용**은 §1-8에서 숫자로 드러났다(로그 printf가 부하 잡을 2.6배로 늘림).
- **infer(12)가 load-low(8)보다 위**: 실제 일이 더미 부하보다 아래로 밀리면 안 된다.
  같은 8로 두면 둘이 라운드로빈을 돌아 부하 잡 완료시간에 잡음이 낀다 —
  즉 축 B를 추가한 것이 축 A의 측정을 오염시킨다.
- **load가 유일한 조작 변수**: 8(정상 배치) ↔ 50(액션 위로 뒤집기). 부하의 *양*은
  독립변수가 아니었다(§1-8). 한 바이너리가 config를 순회해 "빌드가 달라서"라는 교란을 없앴다.

### 윈도우 소유권 — 왜 센서 태스크가 복사하는가

링버퍼 `s_win[128]`의 크기가 윈도우 길이와 **같다**. 윈도우가 완성된 순간부터 10ms 뒤엔
가장 오래된 샘플이 이미 덮인다. 추론 태스크는 우선순위 12라 config B(부하 50)에서 20ms
넘게 못 깨어날 수 있고, 그러면 윈도우 앞부분과 뒷부분이 **서로 다른 시각의 데이터로 찢어진다**
— 그런데 값은 그럴듯해서 조용히 틀린다. 그래서 소유권을 생산자 쪽에 두고, 센서 태스크가
완성 즉시 `s_snap`으로 1,536 B를 복사한 뒤 알림을 보낸다. 추론이 아직 이전 것을 들고 있으면
이번 윈도우는 **버리고 센다**(`drop=`) — 조용히 삼키지 않는 §1-9 원칙 그대로다.

`printf`는 **로그 태스크에서만** 부른다. `HAL_UART_Transmit`은 블로킹이라 115200bps에서
한 줄에 수 ms가 걸린다. 이걸 action 태스크에서 부르면 측정 대상 자체가 오염된다
(probe effect). 측정값은 큐로 넘기고 통계 계산·출력은 전부 로그 태스크 몫이다.

CubeMX가 만든 `defaultTask`는 `osThreadExit()`로 즉시 종료시킨다. 실제 태스크 5개는
전부 `xTaskCreateStatic` — **동적 할당 없음**(CLAUDE.md 규칙). 추론 커널도 malloc을
쓰지 않는다(층간 핑퐁 버퍼가 파일 스코프 static, 48 B).

## 2. 마감시한 이벤트 → 액션 경로

```
TIM2 update ISR ──(1) t0 = DWT->CYCCNT
       │
       └──(2) vTaskNotifyGiveFromISR(action) + portYIELD_FROM_ISR
                     │
                     └──(3) action 태스크 기상: t1 = DWT->CYCCNT
                                  지연 = t1 - t0        ← 측정값
                            (4) HAL_GPIO_TogglePin(LD2) ← 로컬 액션
```

- **이벤트 소스 = TIM2**(내부 전용, 핀 없음, 50ms 주기). 버튼이 아니라 타이머인 이유는
  **결정론과 재현성** — 100회 반복 통계를 사람 손으로 만들 수 없다. (B1 버튼은 예비.)
- ISR은 `HAL_TIM_IRQHandler`를 거치지 않고 UIF만 직접 지운다. HAL 디스패치가 끼면
  그 오버헤드가 측정값에 섞인다. ISR이 하는 일은 **타임스탬프 + 노티피케이션** 둘뿐.
- ISR 우선순위 6 — `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`(5)보다 **낮게**(숫자 크게)
  잡아야 ISR에서 `...FromISR` API를 부를 수 있다. 이걸 어기면 `configASSERT`에 걸린다.
- 이 지연에 포함되는 것: ISR 진입/처리 + 컨텍스트 스위치 + 스케줄러 오버헤드.
  포함되지 않는 것: 없음(액션 직전까지 전부). 즉 **"이벤트가 났는데 실제로 반응하기까지"**의
  전량이고, 그래서 W3에서 우선순위를 흔들면 이 값이 움직인다.

## 3. 측정 규율 (CLAUDE.md)

- **워밍업 16샘플 제외** 후 통계 시작.
- **배치**: 액션 128샘플(≈6.4초), 센서 256샘플(≈2.56초). 배치마다 min/중앙값/p99/max를 출력.
  단발 측정 없음.
- **더블 버퍼 + 소유권 플래그**: 로그 태스크가 한쪽 버퍼를 정렬(`dwt_stats`는 제자리 정렬 =
  파괴적)하는 동안 생산자는 반대쪽에 쌓는다. `busy` 플래그로 소유권을 표시해서, 로그가
  밀렸을 때 생산자가 두 바퀴 돌아 정렬 중인 버퍼를 덮어쓰는 일을 막는다.
  이때 빠진 샘플은 `skip=`으로 보고 — **조용히 버리지 않는다.**
- 원본 단위는 항상 **사이클**. µs는 84MHz(HSI, ±1%) 기준 환산치이므로 절대시간 정밀도는 없다.
- **스택 오버플로 훅**(`configCHECK_FOR_STACK_OVERFLOW=2`): 태스크 스택 끝에 패턴을 깔고
  전환마다 검사한다. 걸리면 `vApplicationStackOverflowHook`이 인터럽트를 끄고 **LD2를
  1초 주기로 토글** — 정상(50ms 토글)과 눈으로 즉시 구분된다. 훅 안에서 printf는 부르지
  않는다(이미 스택이 깨진 상태라 더 깊이 들어가면 원인 정보까지 잃는다).
  잡힌 태스크 이름은 전역 `g_stack_overflow_task`에 남는다.

출력에 같이 찍히는 카운터:

| 필드 | 뜻 | 정상값 |
|---|---|---|
| `miss(1ms)` | 지연이 잠정 마감시한 1ms를 넘은 횟수 | **0** |
| `lost` | 액션이 못 따라가 이벤트가 합쳐진 횟수 | **0** |
| `skip` | 로그 백프레셔로 측정에서 빠진 샘플 | 0 (드물게 >0이어도 무해) |
| `fail` | I2C 읽기 실패 횟수 | **0** |
| `sat` | 가속도/자이로가 포화선(32000 LSB)에 근접한 샘플 수 | **0** — 0이 아니면 풀스케일 레인지를 올려야 한다 |
| `drop` | 추론이 못 따라가 버린 윈도우 수 | **0** (추론은 0.2% 부하라 원리상 안 나야 한다) |
| `bdrop` | 로그 큐 포화로 통째로 못 나간 추론 배치 | **0** |

## 4. 보드에서 확인할 것 (플래시 후)

UART 115200 8N1. 부팅 시 기존 브링업(DWT selftest / I2C 스캔 / MPU6050) 로그가 먼저 나오고,
스케줄러가 시작되면 아래가 반복된다.

```
=== W3 up: action(48) sensor(40) log(16) infer(12) load(8/50) ===
edge: win=128 hop=64 (640ms/추론) debounce=2 batch=128 (81초)
tag,config,n,min,median,p99,max
[SEN] cfg=L0-noload  batch=0 n=256 interval_us med=10000 ... fail=0 skip=0 sat=0 win=... a=(...) g=(...)
[ACT] cfg=L0-noload  batch=0 n=128 lat_us med=... p99=... max=... miss(1ms)=0 lost=0 skip=0
[EDGE] win=1    cfg=L0-noload  err=4143     thr=18372 normal  infer=714.9us lat=741.2us drop=0
[EDGE]* win=137 cfg=A-mono     err=101772   thr=18372 ANOMALY infer=714.2us lat=740.8us drop=0
[AE ] cfg=A-mono     batch=0 n=128 infer_us med=... max=... (min=... cyc) act=2 skip=0 bdrop=0
```

`[EDGE]` 앞의 `*`가 **로컬 액션 발동**이다 — 판정이 정상↔이상으로 전환된 순간.
매 윈도우가 아니라 전환에만 붙는 건 디바운스(연속 2회) 때문이고, 스파이크 하나에
오경보가 나지 않게 하려는 것이다. 대가는 감지 지연 +0.64초(윈도우 1.28초 대비 50%).

체크리스트:

1. **LD2(초록 LED)가 50ms마다 토글** → 육안으로는 10Hz 깜빡임. 이게 "로컬 액션"의 시각 증거.
2. `[ACT]` 줄의 `med`/`p99`/`max`가 µs 단위로 찍히는가 → **W2 DoD의 핵심 수치**.
   `max`가 `med`보다 크게 튀는지 함께 볼 것(선점·ISR 개입의 흔적).
3. `miss(1ms)=0`, `lost=0` — 하나라도 0이 아니면 마감시한 설정이나 부하 가정을 재검토.
4. `[SEN]`의 `interval_us med`가 **10000 근처**인가 → 태스크 환경에서도 100Hz 유지.
   `fail=0`이어야 I2C가 건강한 것.
   (W2 초기 `HAL_Delay` 방식은 11.00ms = 90.9Hz였다 — `dwt_baseline.csv`의
   `imu_interval_haldelay`. 이번 값이 10000에 붙어야 그 문제가 해결된 것.)
5. `a=(x,y,z)`가 보드를 **기울이면** 변하고, `g=(x,y,z)`가 보드를 **돌리면** 변하는가
   → 가속도·자이로 둘 다 살아있다는 생존 신호. 정지 상태에서 자이로는 0 근처
   (바이어스만큼 치우칠 수 있음).
6. `win=`이 계속 증가하는가 → 추론 입력 윈도우가 hop 64마다 쌓이는 중.
   100Hz·hop 64면 **0.64초마다 1개**씩 늘어야 정상.
7. **`sat=`을 볼 것** → 정지에선 0이어야 한다. 실측(2026-08-08): 정지 0,
   충격성 이상에서 22,745샘플 중 15개(0.07%)가 ±2g에 접촉했다. 특징을 망칠 수준은
   아니지만 **한계에 닿는다**는 근거이고, 더 센 진동을 다루려면 `AFS_SEL`을 올려야 한다
   ([mpu6050.h](../firmware/Core/Inc/mpu6050.h) 주석 — 모델 재학습은 불필요).
8. `[EDGE]` 줄이 **0.64초마다** 하나씩 나오는가, `drop=0`인가 → 축 B 파이프라인이
   실시간으로 따라가고 있다는 증거.
9. 보드를 가만히 뒀을 때 `normal`, 흔들었을 때 `ANOMALY`로 뒤집히는가 →
   **축 B 데모 그 자체.** 실측(2026-08-08): 정지 err 중앙 4,989 / 흔듦 121,626,
   임계 18,372에서 **24배 분리, 겹침 없음**.
   ⚠️ 모델은 **이 보드·이 각도**의 데이터로 학습됐다. 센서를 다시 꽂거나 각도가 1.5°만
   바뀌어도 이상으로 본다(system-design.md §4 "장착 각도 민감도"). 데모 전에 각도가
   수집 때와 같은지 확인할 것 — 다르면 재수집·재학습이다.

수치를 `measurements/*.csv`에 옮겨 적을 때는 CSV 줄(`action_latency,...`, `inference_cycles,...`)을
그대로 쓰고 `clock_hz,measured_at,note` 열을 채운다 ([dwt_baseline.csv](../measurements/dwt_baseline.csv)와 동일 규약).

## 5. 두 축이 만나는 지점

축 A(스케줄링)와 축 B(엣지 추론)는 같은 바이너리 안에서 서로를 건드린다. 그 접점이
**측정으로 보이게** 배선돼 있다:

- `[AE ]`·`[EDGE]` 줄에 **config 이름이 같이 찍힌다.** 즉 "B-mono(부하가 액션 위)에서
  추론 판정 지연이 어떻게 되는가"를 같은 로그에서 대조할 수 있다.
- **나쁜 config는 축 B의 *정확도*까지 건드린다.** config B/C/D에서는 센서 주기가
  1.6~30 ms로 흔들린다(§1-8 실측). 특징 추출은 "샘플이 100Hz 등간격"을 가정하므로,
  주기가 흔들린 구간의 윈도우는 학습 분포와 다른 것이 된다. **스케줄링 실패가
  기능 실패로 번지는 경로**이고, 이건 축 A가 왜 중요한지에 대한 축 B의 답이다.
- 반대 방향(축 B → 축 A)도 있다: 추론 태스크와 `[EDGE]` 한 줄이 늘어난 만큼
  로그 태스크의 printf가 늘었다. 로그(16)는 부하(8)보다 위라 **A-mono의 부하 잡
  완료시간이 이전 측정보다 나빠질 수 있다.** 그래서 W3 최종 수치는 이 바이너리로
  **다시 잰다** — 이전 스윕 결과를 그대로 들고 가지 않는다.

측정 경로 두 갈래를 헷갈리지 말 것:

| | 어디서 | 재는 것 | 산출물 |
|---|---|---|---|
| `ae_bench()` | 부팅 시, 스케줄러 **전** | 커널 자체 (선점 없음), float32 vs int8 | `kernel_compare.csv` |
| `prv_infer_task` | 스케줄러 안, 매 윈도우 | 시스템 안에서의 실제 소요 (선점 포함) | `inference_cycles.csv` |

전자의 합계 41,790 cyc vs 후자의 min 59,911 cyc. 차이 18,121 cyc(215.7 µs)는
`prv_window_to_float`(raw int16 768개 → g/dps)이고, **커널 두 파일만 O2로 고정했고
`app_tasks.c`는 Debug -O0**이라 그 상당 부분이 최적화 수준의 값이다. 즉 "min이 커널
벤치와 같아야 한다"는 예상은 사이에 -O0 코드가 낀 만큼 어긋났고, **어긋난 양이 정확히
설명된다**는 게 확인이다.

## 6. 수집 모드 — 같은 바이너리의 다른 진입점

**B1(파란 버튼)을 누른 채 리셋**하면 스케줄러로 안 가고
[collect.c](../firmware/Core/Src/collect.c)로 빠진다. 세션을 순서대로 안내하며
raw 6축을 100 Hz CSV로 UART에 뱉고, 끝나면 정지한다(스케줄러가 시작되면 로그 태스크가
UART를 같이 써서 사용자가 로그를 저장하기도 전에 화면이 덮인다).

| 결정 | 왜 |
|---|---|
| 별도 빌드가 아니라 **부팅 시 분기** | 수집용/실행용 바이너리를 나누면 학습 데이터가 어느 센서 설정에서 나온 건지 보장이 안 된다. 같은 `mpu6050_configure()`를 거친 뒤 갈라지므로 **구조적으로 같은 설정** |
| B1 검사를 **부팅 맨 앞**에서 | 브링업(~6초) 뒤에 보면 사용자가 6초 넘게 버튼을 잡고 있어야 한다. 실제로 이것 때문에 한 번 실패했다 |
| 주기를 **DWT 절대 시각**으로 | `HAL_Delay(10)`은 실측 11.00 ms(=90.9 Hz). 그대로 쓰면 학습은 90.9 Hz, 추론은 100 Hz인 데이터가 만들어진다 |
| 실패한 샘플은 **안 쓴다** | 앞 값을 복제하면 `std`/`mad`가 거짓이 된다. 대신 `t_ms`에 구멍이 남고, 임포터가 그 경계에서 윈도우를 자른다 |
| raw LSB로 출력 | `--specs=nano.specs`라 `printf("%f")`가 링크에서 빠진다. 정수가 짧아 UART 대역폭도 아낀다(한 줄 ~4.3 ms < 10 ms 예산) |
