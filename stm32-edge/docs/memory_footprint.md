# 메모리 풋프린트 — flash / RAM / 아레나 / 태스크별 스택

> 대상 바이너리: `firmware/Debug/stm32-edge.elf` (W4, 스택 high-water 계측 포함 빌드)
> 방법: `arm-none-eabi-size` + 최종 ELF의 `nm -S` 심볼 합산. **`.map`의 심볼 나열을
> 그대로 합치면 안 된다** — `--gc-sections`가 버린 조각(예: 헤더 include로 TU마다
> 생기는 가중치 사본)까지 세어 과대계상된다. 실제로 float 가중치가 map에는 4벌
> 보이지만 최종 이미지에는 1벌만 남는다.

## 0. 요약

| | 사용 | 전체 | 비율 |
|---|---:|---:|---:|
| **Flash** (.text + .data) | 64,024 B | 512 KB | **12.2 %** |
| **RAM 정적** (.data + .bss) | 45,096 B | 128 KB | **34.4 %** |
| + 링커 예약 (MSP 스택 1,024 + 최소 힙 512) | 1,536 B | | +1.2 % |

Debug -O0 빌드 기준이다(커널 두 파일만 O2 고정 — `ae_infer.c` 상단 주석).
릴리스 최적화 전인데도 Flash 8배·RAM 3배의 여유가 있어, 이 규모에서는
크기 최적화가 **문제가 아니라는 것** 자체가 측정 결과다.

## 1. Flash 분해 — 모델은 어디에 얼마나 사는가

`.text` 63,916 B의 대부분은 HAL(I2C/TIM/UART)과 FreeRTOS 커널이다.
모델 관련 상수(rodata)는 다음과 같다(최종 이미지 심볼 합):

| 항목 | 크기 | 비고 |
|---|---:|---|
| int8 경로 (가중치+바이어스+양자화 상수+포인터 테이블) | ≈1,088 B | 실전 추론이 쓰는 전부 |
| float32 경로 (가중치+바이어스) | 2,928 B | 커널 비교(`ae_bench`)·검증용 |
| 정규화 상수 (`ae_norm_mean/std`, 두 경로 공용) | 192 B | float — z-score가 물리 단위 기준 |
| 벤치 테스트벡터 (`ae_tv_*`) | 6,168 B | 부팅 자가검증·커널 벤치 전용. 릴리스에서 뺄 수 있는 몫 |

읽는 법: **"모델이 Flash를 얼마나 쓰나"의 정직한 답은 용도에 따라 다르다.**
추론만 남기면 ~1.3 KB(int8+정규화), 지금 바이너리는 비교·자가검증 장비까지 싣고
~10.4 KB다. README·`kernel_compare.csv`의 "int8 절약분 2,016 B"는 W3에서 export
산출물 기준으로 계산한 값이라 이 표의 심볼 묶음과 경계가 조금 다르다 —
어느 쪽으로 세어도 결론은 같다: **이 규모에서 양자화가 아끼는 Flash는 ~2 KB,
512 KB의 반 퍼센트가 안 된다.**

## 2. RAM 분해 — .bss 44,988 B는 누구 것인가

| 묶음 | 크기 | 내용 |
|---|---:|---|
| FreeRTOS 힙 `ucHeap` | 15,360 B | §4 참조 — 실사용은 CubeMX `defaultTask` 생성분(~0.7 KB)뿐 |
| 앱 태스크 스택 5개 | 6,656 B | §3 표 |
| 추론 데이터 경로 | 6,192 B | `s_winf` 3,072 + `s_win` 1,536 + `s_snap` 1,536 + 커널 핑퐁 48 |
| 측정 더블버퍼 | 5,120 B | `s_sen_int` 2,048 + `s_act_lat`/`s_inf_job` 각 1,024 + `s_ae_cyc`/`s_ae_lat` 각 512 |
| 부팅 커널 벤치 버퍼 `s_cyc_*` | 3,200 B | 800 B × 4. 스케줄러 시작 전만 쓰고 안 놓는다 — 정적 설계의 대가 |
| FreeRTOS 커널 구조체 + 타이머 태스크 스택 | ≈3,300 B | `pxReadyTasksLists` 1,120, `Timer_Stack` 1,024 등 |
| 기타 (HAL 핸들, 로그 큐, UART 버퍼 등) | 나머지 | |

**"아레나"에 해당하는 것**: 이 펌웨어는 별도 아레나 할당자 없이 전부 파일 스코프
정적 버퍼다(추론 한정으로는 층간 핑퐁 48 B + 입력 `s_winf` 3,072 B가 작업 메모리의
전부). malloc은 앱 코드에서 0회 — 예외는 §4의 CubeMX 잔재 하나다.

## 3. 태스크별 스택 — 배정 vs 실측 high-water

배정치는 `app_tasks.c`의 `STK_*`(워드, 1워드=4 B). **high-water는 "여태 가장
얕게 남았던 잔여"라 값이 클수록 여유가 큰 것**이고, 스윕 바퀴가 거듭돼도 같은
숫자면 수렴한 것이다.

| 태스크 | 배정 (워드) | 잔여 최소 (워드) | 사용 최대 (워드) | 여유율 |
|---|---:|---:|---:|---:|
| action (48) | 256 | *실측 대기* | | |
| sensor (40) | 384 | *실측 대기* | | |
| log (16) | 512 | *실측 대기* | | |
| infer (12) | 320 | *실측 대기* | | |
| load (8/50) | 192 | *실측 대기* | | |

### 실측 절차 (보드 필요 — W4 유일의 보드 항목)

1. 이 빌드를 플래시하고 UART(115200 8N1)를 연다.
2. 스윕이 한 바퀴 돌 때마다(128초) `[STK]` 한 줄이 나온다:
   `[STK] sweep=1 잔여최소/총량(워드): action=NNN/256 sensor=NNN/384 ...`
3. **sweep=2와 sweep=3의 값이 같아질 때까지** 기다린다(~6.5분). 늘고 있으면
   아직 최악 경로를 못 본 것이다 — 그 상태의 값을 적으면 단발 측정과 같다.
4. 수렴한 줄을 위 표에 옮기고, 이 문서 상단의 *실측 대기*를 지운다.
   보드를 흔들어 ANOMALY 전환(디바운스·액션 경로)도 한 번 태우고 확인하면 완전하다.

조회는 로그 태스크가 한다 — `uxTaskGetStackHighWaterMark`는 스택 영역을 스캔하므로
측정 대상 태스크의 경로에 그 비용을 섞지 않는다(printf 규칙과 같은 이유).
오버플로 훅(`configCHECK_FOR_STACK_OVERFLOW=2`)은 사후 검출이고, high-water는
**사전 여유 측정**이다 — 훅이 안 걸렸다고 여유가 충분한 게 아니다.

## 4. 정직한 각주 — FreeRTOS 힙 15,360 B의 정체

`configTOTAL_HEAP_SIZE=15360`(heap_4)이 .bss의 34%를 차지하는데, 실제 소비자는
CubeMX가 생성한 `defaultTask`(osThreadNew 동적 생성, 스택 512 B + TCB) 하나뿐이다 —
그마저 `osThreadExit()`로 즉시 종료된다. 앱 태스크 5개·큐·타이머 태스크 스택은
전부 정적이다. 즉 **"malloc 0회"는 앱 코드 기준으로 참이고, CubeMX 잔재가
힙에서 ~0.7 KB를 한 번 쓴다.** 힙을 1~2 KB로 줄이면 RAM 13 KB가 돌아오지만,
`.ioc` 재생성(CubeMX 소관 = 사용자 작업)과 얽혀 있어 W4에서는 기록만 남긴다 —
지금 RAM 사용률 34%에서 이 회수는 필요가 아니라 선택이다.
