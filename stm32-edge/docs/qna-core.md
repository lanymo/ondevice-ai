# 핵심 개념 Q&A — 코드에서 겪은 일 → 개념 순서

> 읽는 법: 각 질문은 **내 리포의 실제 코드/출력에서 시작**한다. 답을 먼저 가리고
> 스스로 말해본 뒤 펼쳐 볼 것. 면접 꼬리질문이 나올 만한 지점은 ❓로 표시.
> (범위: W2까지 — UART printf, DWT, MPU6050 I2C, **FreeRTOS 태스크 구조**)
> A~D는 겪고 나서 쓴 절, **E는 아직 절반만 겪은 절** — E0(용어)부터 읽고,
> E9의 확인 목록을 들고 플래시하면 나머지 절반이 채워진다.

## A. UART printf — 생명줄

### Q1. 보드의 printf가 어떻게 내 PC 터미널에 찍히는 걸까?

경로는 4단계다.

1. `printf("...")`를 부르면 C 표준 라이브러리(newlib)가 문자열을 만든 뒤, 최종 출력을 **`_write()`라는 함수에 위임**한다. `syscalls.c:80`의 `_write`가 `__attribute__((weak))`(약한 정의)로 되어 있어서, 우리가 `main.c:69`에 같은 이름의 함수를 만들면 그쪽이 대신 불린다. → "printf 리타겟"
2. 우리 `_write`는 받은 바이트를 `HAL_UART_Transmit(&huart2, ...)`로 **USART2 주변장치**에 밀어 넣는다.
3. USART2는 PA2(TX)/PA3(RX) 핀으로 비트를 내보낸다 (`usart.c:72-75`).
4. Nucleo 보드 위의 **ST-LINK 칩이 이 UART 신호를 USB 가상 COM 포트로 변환** → PC에서 시리얼 터미널(115200)로 보인다.

❓꼬리질문: "왜 115200 8N1인가?" → 115200비트/초, 데이터 8비트, 패리티 없음(N), 스톱 1비트. 양쪽이 미리 약속해야 하는 값이고(`usart.c:42-45`), 터미널 설정이 다르면 깨진 글자가 나온다.

### Q2. `setvbuf(stdout, NULL, _IONBF, 0)`은 왜 있나? (main.c:109)

newlib의 printf는 기본적으로 **첫 호출 때 출력 버퍼를 malloc으로 할당**한다. 우리 규칙은 "펌웨어에서 malloc 금지"인데, printf가 뒤에서 몰래 어기는 셈이 된다. `_IONBF`(버퍼링 없음)로 바꾸면 버퍼 할당 경로 자체가 사라진다.

❓왜 malloc 금지인가 → 시스템 디자인 §S4.

## B. DWT — 측정의 기반

### Q3. DWT는 뭘 세는 건가?

**CPU 코어 안에 내장된 디버그 유닛**(Data Watchpoint and Trace)이고, 그 안의 `CYCCNT`라는 32비트 레지스터가 **CPU 클럭 사이클마다 1씩 증가**한다. 84MHz에서 1사이클 ≈ 11.9ns.

왜 이게 필요한가: `HAL_GetTick()`은 해상도가 1ms다. 우리가 잴 대상(추론 1회, I2C 읽기 1회)은 수십 µs~수 ms라서 1ms 눈금으로는 잴 수 없다. DWT는 소프트웨어 개입 없이 하드웨어가 세므로 오버헤드도 수 사이클뿐 — `dwt.c`의 selftest [3]에서 실측한 그 값이다.

### Q4. `dwt_init()`에서 왜 TRCENA를 먼저 켜야 하나? (dwt.c:24)

DWT는 "디버그/트레이스 서브시스템" 소속이라 평소엔 꺼져 있다. `DEMCR.TRCENA` 비트가 그 서브시스템 전체의 전원 스위치 격이고, 이걸 켜기 전에는 DWT 레지스터에 써도 무시된다. 순서가 강제되는 이유다: TRCENA → CYCCNT=0 → CYCCNTENA.

❓꼬리질문: "32비트 카운터면 오버플로우는?" → 84MHz에서 2³²/84M ≈ **51초마다 한 바퀴** 돈다. 하지만 우리는 항상 `t1 - t0` 차이만 쓰는데, C의 unsigned 뺄셈은 모듈로 연산이라 **구간이 51초 이내면 랩을 걸쳐도 결과가 정확**하다. (그래서 절대값이 아니라 항상 구간 측정만 한다.)

### Q5. selftest의 [1] alive / [2] scale / [3] overhead는 각각 뭘 검증하나?

측정 도구를 검증 없이 믿지 않기 위한 3중 체크다 — "자로 재기 전에 자부터 검사".

- **[1] alive**: 카운터가 실제로 증가하는가. (루프 변수에 `volatile`을 붙인 이유: 컴파일러가 빈 루프를 통째로 삭제해버리는 걸 막으려고. dwt.c:127)
- **[2] scale**: 눈금이 맞는가 — `HAL_Delay(100ms)`라는 이미 아는 길이와 대조. 기대값을 상수로 박지 않고 `SystemCoreClock`에서 계산한다(클럭 설정이 바뀌면 기대값도 따라 바뀌도록).
- **[3] overhead**: 측정 행위 자체가 몇 사이클을 먹는가 — 빈 구간을 100번 재서 바닥값을 안다. 이보다 작은 차이는 논할 수 없다.

❓꼬리질문 (dwt.c:155-158 주석): "허용 오차가 왜 -1%~+5%로 비대칭인가?" → `HAL_Delay`는 "**최소** 그만큼"을 보장하려고 1틱을 더 기다린다. 즉 항상 약간 길게 나오는 게 정상이고, 짧게 나오면 오히려 이상하다.

### Q6. 왜 평균이 아니라 중앙값·p99·max인가? 왜 단발 측정 금지인가?

실시간 시스템의 질문은 "평균적으로 빠른가"가 아니라 "**최악의 경우에도 마감시한을 지키는가**"다. 평균은 가끔 튀는 값(인터럽트 개입, 캐시 미스)을 숨긴다.

- **중앙값(median)**: 대표값. outlier에 강해서 평균보다 낫다.
- **p99**: 100번 중 99번은 이 값 이내 — "거의 항상"의 상한.
- **max**: 관측된 최악 — 하드 마감시한 논의는 이걸로 한다.

단발 측정은 그 1회가 운 좋은 회차인지 나쁜 회차인지 알 수 없어서 금지. **워밍업 제외** 이유: 첫 몇 회는 캐시/플래시 가속기가 채워지기 전이라 항상 느리게 나오는데, 이건 정상 상태가 아니라 시작 비용이다.

## C. I2C & MPU6050 — 센서 브링업

### Q7. I2C가 뭔지 한 문단으로.

**선 2개(SDA=데이터, SCL=클럭)를 여러 장치가 공유하는 버스**. 마스터(STM32)가 클럭을 만들고, 매 통신을 "주소 부르기"로 시작해서 그 주소의 슬레이브(MPU6050)만 응답한다. 선을 공유하는 방식이 오픈드레인(장치는 선을 끌어내리기만 하고, 놓으면 **풀업 저항**이 High로 되돌림)이라 풀업이 없으면 버스가 아예 동작하지 않는다 — GY-521 모듈에는 풀업이 내장돼 있어서 우리는 그냥 됐던 것.

### Q8. MPU6050 주소가 왜 0x68인가? (mpu6050.h:25)

I2C 주소는 7비트고, MPU6050은 상위 6비트가 고정 + **마지막 1비트를 AD0 핀 전압으로 결정**한다: AD0=GND → 0x68, AD0=VCC → 0x69. 이렇게 만든 이유는 같은 센서 2개를 한 버스에 붙일 수 있게 하려고(주소 충돌 회피). GY-521은 AD0을 기본 GND로 당겨놔서 0x68이 나온다.

### Q9. 그런데 HAL 함수에는 왜 `0x68 << 1`을 넘겼지? (i2c_scan.c:28, mpu6050.c:12)

I2C 전선 위에서 첫 바이트는 `[7비트 주소][R/W 1비트]` 구조다. ST HAL은 이 **전선 형식 그대로의 8비트 값**을 받기로 한 API라서 7비트 주소를 왼쪽으로 1비트 밀어 넘겨야 한다. 그냥 0x68을 넘기면 전선에는 0x34를 부르는 셈이 되어 **아무도 응답하지 않는다** — 배선이 완벽해도 스캔에 안 뜨는, 실제로 흔한 첫 삽질 포인트.

❓꼬리질문: "스캔을 왜 0x08~0x77만 도나?" (i2c_scan.c:11) → 양끝 주소들은 I2C 표준의 예약 주소(general call 등)라 장치 주소로 안 쓴다.

### Q10. WHO_AM_I가 뭐고, 왜 값이 0x68이 아니어도 실패시키지 않았나?

WHO_AM_I(레지스터 0x75)는 칩이 자기 ID를 돌려주는 읽기 전용 레지스터로, 사실상 **"통신이 제대로 되는가"의 자기검증**이다 — 주소·배선·프로토콜 중 하나라도 틀리면 이 값이 나올 수 없다.

값으로 합/불을 가르지 않은 이유(mpu6050.h:47-50): GY-521이라는 이름으로 팔리는 모듈에 실제로는 MPU-6500(0x70)이나 9250(0x71) 다이가 들어 있는 경우가 흔한데, **우리가 쓰는 레지스터(PWR_MGMT_1, ACCEL_XOUT_H)는 세 칩이 동일**해서 그대로 동작한다. 그래서 "읽기 성공"만 판정하고, 진짜 판정은 [4]단계 "움직이면 값이 변하는가"로 한다.

### Q11. sleep 해제는 왜 해야 했나? (mpu6050.c:67 `mpu6050_wake`)

MPU6050은 **리셋 직후 PWR_MGMT_1(0x6B) 레지스터의 SLEEP 비트(bit6)가 1** — 즉 절전 모드로 켜진다(전원만 넣고 방치되는 제품 상황을 위한 기본값). 이 상태에서도 I2C 통신은 되기 때문에 "WHO_AM_I는 성공하는데 가속도가 계속 0"이라는, 배선 탓으로 착각하기 딱 좋은 증상이 나온다. PLAN.md의 "값 0 고정 → 전원관리 sleep 해제"가 바로 이것.

코드에서 볼 것 두 가지:

- **read-modify-write** (mpu6050.c:71-83): 레지스터를 읽고, SLEEP 비트만 지우고, 되쓴다. 통째로 0을 쓰면 같은 레지스터의 다른 설정(클럭 소스 선택 등)까지 날아가기 때문.
- **쓰고 나서 다시 읽어 확인** (mpu6050.c:86-92): "썼으니 됐겠지"가 아니라 실제로 지워졌는지 검증. 측정 규율과 같은 태도다.

### Q12. 가속도를 왜 6바이트 연속 읽기로 가져오나? (mpu6050.c:99)

ACCEL_XOUT_H(0x3B)부터 XH,XL,YH,YL,ZH,ZL 6바이트가 연속 배치돼 있고, **한 트랜잭션으로 읽어야 3축이 같은 시점의 값**이 된다. 축마다 따로 읽으면 그 사이에 센서가 값을 갱신해서 서로 다른 시점이 섞인다.

받은 바이트는 **빅엔디안**(상위 바이트 먼저)이라 `(b[0]<<8)|b[1]`로 조합하고, int16_t로 캐스팅하면 2의 보수 음수가 그대로 살아난다 (mpu6050.c:107-110).

### Q13. "1g = 16384 LSB"는 무슨 뜻인가? (mpu6050.h:35)

센서는 물리량(가속도)을 int16(−32768~+32767)로 내보낸다. 풀스케일이 ±2g(리셋 기본값)이므로 2g ↔ 32768, 즉 1g ↔ 16384. 보드를 평평히 두면 z축에 중력 1g ≈ 16384 근처가 찍히는 게 정상이다.

이건 **"연속 물리량 ↔ 정수 표현" 매핑의 첫 사례**로, W3에서 할 int8 양자화(float 가중치 ↔ int8 + scale)와 정확히 같은 아이디어다. 센서는 하드웨어가 해준 양자화, 모델은 우리가 할 양자화.

## D. 클럭 — 모든 측정의 전제

### Q14. "84MHz HSI"가 뭐고, ±1% 오차는 무슨 의미인가?

STM32F411 내부의 RC 오실레이터(HSI, 16MHz)를 PLL이라는 체배 회로로 84MHz까지 올려서 CPU 클럭으로 쓴다. HSI는 수정 진동자(크리스탈)가 아니라서 주파수가 **±1% 정도 부정확**하다.

이게 측정에 주는 영향을 구분하는 게 중요하다:

- **사이클 수 측정 (우리의 주 지표)**: 영향 없음. "추론이 N사이클"은 클럭이 몇 Hz든 참이다.
- **절대 시간 환산 (ms로 표시할 때)**: ±1% 오차 포함. "약 X ms"로 읽어야 한다.
- **DWT selftest [2]가 통과한 이유** (dwt.c:158 주석): DWT와 HAL 틱(TIM10)이 **같은 HSI에서 파생**되므로 클럭이 1% 빗나가도 둘 다 같이 빗나가 비율은 유지된다.

❓꼬리질문: "HAL 틱이 왜 SysTick이 아니라 TIM10인가?" → FreeRTOS가 SysTick을 자기 스케줄러 틱으로 가져가기 때문에, HAL은 다른 타이머(TIM10)로 밀어냈다 (CubeMX가 경고하는 표준 패턴).

## E. FreeRTOS 태스크 구조 — 마감시한 이벤트 경로

> 대상 코드: `firmware/Core/Src/app_tasks.c`, 설계 배경: `docs/task-architecture.md`
> **주의**: A~D는 "직접 겪고 나서" 쓴 절이지만, 이 절은 **아직 안 겪은 것**이 섞여 있다.
> 보드에 플래시해서 `[ACT]` 수치를 보기 전까지는 절반은 남의 이야기다. 그러니
> 여기 있는 건 "외울 것"이 아니라 **플래시할 때 확인할 목록**으로 읽는 게 맞다.

### E0. 먼저 용어 — 이거 없이는 아래가 안 읽힌다

| 용어 | 한 줄 정의 | 이 프로젝트에서 |
|---|---|---|
| **ISR** (인터럽트 서비스 루틴) | 하드웨어가 "지금!" 하고 강제로 부르는 함수. **내가 부르는 게 아니다** | `TIM2_IRQHandler()` (app_tasks.c:157) |
| **인터럽트 우선순위** | 인터럽트끼리 겹쳤을 때 누가 먼저. **숫자가 작을수록 높다** | TIM2 = 6 |
| **태스크 우선순위** | FreeRTOS 태스크끼리의 순서. **숫자가 클수록 높다 (인터럽트와 반대!)** | action=48, infer=8 |
| **선점**(preemption) | 높은 우선순위가 준비되면 낮은 걸 **중간에 끊고** CPU를 뺏음 | action이 infer를 끊는다 |
| **컨텍스트 스위치** | CPU가 태스크 A→B로 갈아타는 일. 레지스터를 저장하고 복원 | 이 비용이 "지연"에 포함된다 |
| **블록**(blocked) | 태스크가 "무슨 일이 생길 때까지" 자면서 CPU를 안 쓰는 상태 | action은 평소 블록돼 있다 |
| **태스크 노티피케이션** | ISR이나 태스크가 특정 태스크 하나를 깨우는 가장 가벼운 신호 | `vTaskNotifyGiveFromISR` |
| **레이스**(race condition) | 두 실행 흐름이 같은 데이터를 동시에 건드려 생기는 버그 | 더블버퍼에서 실제로 났었다 (E5) |

**"인터럽트는 숫자 작을수록 높고, 태스크는 숫자 클수록 높다"** — 이 반대 방향이 처음에
제일 헷갈리는 지점이다. 인터럽트 쪽은 ARM이 정한 하드웨어 규칙이고, 태스크 쪽은
FreeRTOS가 정한 소프트웨어 규칙이라 서로 상관이 없어서 이렇게 됐다.

### E1. TIM2 ISR부터 LD2 토글까지, 무슨 일이 일어나는가 (전체 흐름)

이 절의 중심 질문. 5단계다.

1. **TIM2가 50ms를 센다.** TIM2는 타이머 주변장치로, 1µs마다 1씩 올라가는 카운터다.
   49999까지 세면 0으로 돌아가면서 "업데이트 이벤트"를 낸다 → 50ms 주기 (app_tasks.c:133-135).
2. **하드웨어가 `TIM2_IRQHandler()`를 강제로 호출한다.** 지금 CPU가 무슨 태스크를 돌리고
   있었든 상관없이 중단하고 이 함수로 점프한다. 이 함수 안에서 두 가지만 한다:
   - **지금 시각을 찍는다**: `s_event_t0 = dwt_now()` ← 이게 "이벤트가 난 순간"
   - **action 태스크를 깨운다**: `vTaskNotifyGiveFromISR(s_action_task, ...)`
3. **`portYIELD_FROM_ISR(hpw)`** — "방금 깨운 태스크가 지금 돌고 있던 태스크보다 우선순위가
   높으면, ISR이 끝나는 즉시 그쪽으로 갈아타라"는 요청. action(48)은 최상위라 항상 참이다.
4. **action 태스크가 깨어난다.** `ulTaskNotifyTake(...)`에서 자고 있다가 리턴하고,
   **바로 다음 줄에서 다시 시각을 찍는다**: `lat = dwt_now() - s_event_t0` (app_tasks.c:195-196).
   → **이 차이가 "이벤트→액션 지연"이다.**
5. **LD2를 토글한다** (app_tasks.c:198). 이게 "로컬 액션". 실제 제품이라면 여기가
   경고음이거나 밸브를 잠그는 자리다.

즉 **지연에 포함되는 것**: ISR 진입 비용 + ISR 실행 + 컨텍스트 스위치 + 스케줄러 오버헤드.
**포함 안 되는 것**: 없다. 이벤트 발생부터 실제 반응 직전까지 전부다.

❓꼬리질문: "왜 ISR에서 바로 LD2를 토글하지 않나? 그게 제일 빠른데?" → 맞다, 더 빠르다.
하지만 그러면 **재는 대상이 사라진다.** 우리가 알고 싶은 건 "RTOS 태스크로 반응할 때의
지연"이고, W3에서 우선순위를 바꾸면 이 값이 어떻게 변하는지가 축 A 실험의 전부다.
ISR에서 다 처리하면 항상 빠르지만 실험할 게 없다. (실무에서도 ISR은 짧게 두고
태스크로 넘기는 게 원칙 — ISR이 길면 다른 인터럽트가 밀린다.)

### E2. ISR 우선순위가 왜 하필 6인가? (app_tasks.c:147)

**이게 이 절에서 제일 안 겪어본 개념**이고, 틀리면 조용히 죽는 종류라 중요하다.

먼저 사실 하나: **FreeRTOS API 중 일부는 자기 내부 자료구조(태스크 대기열 같은 것)를
보호하려고 "잠깐 인터럽트를 막는다."** 안 막으면 대기열을 고치는 도중에 ISR이 끼어들어
같은 대기열을 건드릴 수 있고, 그러면 깨진다.

그런데 Cortex-M은 인터럽트를 **전부 막거나 / 전부 열거나**가 아니라,
**"우선순위 N보다 낮은 것만 막기"**가 가능하다(BASEPRI 레지스터). FreeRTOS는 이걸 쓴다.

그 N이 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5` (FreeRTOSConfig.h:142)다.
해석하면: **"우선순위 5보다 낮은(= 숫자가 5 이상인) 인터럽트만 내가 막을 수 있다."**

그래서 규칙이 나온다:

- 내 ISR이 **숫자 5 이상** → FreeRTOS가 막을 수 있음 → 그 안에서 `...FromISR` API **사용 가능**
- 내 ISR이 **숫자 4 이하** → FreeRTOS가 못 막음 → 그 안에서 API를 부르면 **보호가 뚫림**

TIM2를 6으로 준 건 5 이상이라 안전한 값이기 때문이다. 만약 0이나 1을 줬다면?
`configASSERT`에 걸려서 무한 루프에 빠지거나(디버그 빌드), 운 나쁘면 **가끔씩만 죽는**
최악의 버그가 된다.

❓꼬리질문: "그럼 왜 5가 아니라 6인가?" → 5도 규칙상 된다(5 이상이므로). 6은 여유를
한 칸 둔 것뿐이다. 중요한 건 정확한 숫자가 아니라 **5 이상이어야 한다는 경계**다.

❓꼬리질문: "이름에 `FromISR`이 붙은 함수와 안 붙은 함수는 뭐가 다른가?" → ISR 안에서는
"블록"이라는 개념이 없다(ISR은 잘 수 없다). 그래서 ISR용 함수는 대기 옵션이 없고,
대신 "네가 깨운 태스크가 더 급하냐"를 `pxHigherPriorityTaskWoken` 인자로 알려준다.
ISR에서 일반 버전을 부르면 안 된다.

### E3. `vTaskDelay`와 `vTaskDelayUntil`은 뭐가 다른가? (app_tasks.c:265)

100Hz 폴링에서 실제로 문제가 됐던 부분이다.

- **`vTaskDelay(10ms)`** = "**지금부터** 10ms 자라". 그런데 깨어나서 I2C를 읽는 데 1.5ms가
  걸리므로 다음 주기는 10 + 1.5 = **11.5ms**가 된다. 오차가 매번 누적된다.
- **`vTaskDelayUntil(&last, 10ms)`** = "**지난번 깨어난 시각 기준으로** 10ms 뒤에 깨워라".
  작업에 얼마가 걸렸든 주기는 10ms로 유지된다.

`dwt_baseline.csv`의 `imu_interval_haldelay` 행이 바로 이 문제의 증거다 — `HAL_Delay(10)`
방식이라 **중앙값 11.00ms = 90.9Hz**가 나왔다. 목표 100Hz가 아니었던 것.
그래서 태스크로 옮기면서 `vTaskDelayUntil`로 바꿨고, **이번 플래시에서 10000µs 근처가
나오는지 확인하는 게 그 수정의 검증**이다.

❓왜 중요한가: 모델(`model/config.py`)이 **100Hz 전제로 학습**돼 있다. 실제가 90.9Hz면
같은 진동도 다른 주파수로 보여서 특징이 어긋난다.

### E4. 태스크 노티피케이션은 왜 큐나 세마포어 대신인가?

셋 다 "깨우기"를 할 수 있지만 비용과 용도가 다르다.

- **큐**: 데이터를 같이 넘길 때. 내부에 버퍼와 대기열이 있어 제일 무겁다. → 로그 경로에서 씀
- **세마포어**: 개수만 세는 신호. 큐보다 가볍다
- **태스크 노티피케이션**: **특정 태스크 하나**에게 보내는 신호. 태스크 구조체 안의 값
  하나를 건드리는 것이라 제일 빠르다(별도 객체가 없음)

마감시한 경로는 **1대1이고 데이터가 필요 없다**(시각은 전역 변수로 이미 넘겼다).
가장 빠른 수단을 골라야 지연 측정이 "RTOS 오버헤드"를 재는 게 되지 "내가 무거운 걸 골라서
느린 것"을 재는 게 아니게 된다.

❓꼬리질문: "`ulTaskNotifyTake`의 리턴값 `nvals`는 뭔가?" (app_tasks.c:195) → 깨어나기 전까지
쌓인 알림 횟수. **2 이상이면 이벤트를 놓친 것**이다 — 액션이 50ms 안에 못 따라갔다는 뜻이라
`lost` 카운터로 보고한다. 출력에서 `lost=0`을 확인하는 이유.

### E5. 더블버퍼는 왜 필요했나 — 실제로 났던 레이스

`docs/qna-core.md`의 "임베디드 C 단골 질문" 5번에 "ISR과 태스크가 변수를 공유할 때 생기는
문제(race)와 해법 — W2 후반에 직접 겪을 것"이라고 적어뒀는데, **실제로 겪은 게 이것**이다.

문제의 출발: 통계를 내려면 `dwt_stats()`가 배열을 **정렬**해야 한다(중앙값·p99를 뽑으려면
순서를 세워야 하므로). 그런데 정렬은 **배열을 제자리에서 뒤섞는다** — 원본이 파괴된다.

그래서 이런 상황이 생긴다:

```
로그 태스크: [배열 A를 정렬하는 중...]
액션 태스크: [배열 A에 새 측정값을 씀]     ← 정렬 결과가 엉망이 된다
```

**1차 해법 — 더블버퍼**: 배열을 2개 두고 번갈아 쓴다. 로그가 A를 정렬하는 동안 액션은 B에
쌓는다. 대부분 이걸로 끝난다.

**그런데 구멍이 있었다**: 로그 태스크가 밀리면(추론 부하 때문에 CPU를 못 받으면) 액션이
B까지 다 채우고 **두 바퀴 돌아 A로 돌아온다.** 그때 로그가 아직 A를 정렬 중이면 똑같은
문제가 다시 난다. 확률은 낮지만 **낮은 확률로 나는 버그가 제일 나쁘다** — 재현이 안 돼서
원인을 못 찾는다.

**2차 해법 — 소유권 플래그**: `s_act_busy[side]`가 "이 버퍼는 지금 로그 태스크 것"을
표시한다(app_tasks.c:214). 액션은 쓰기 전에 확인하고, 남의 것이면 **그 샘플을 버린다.**
로그는 다 쓰고 나서 플래그를 0으로 되돌린다.

그리고 버린 샘플을 **조용히 버리지 않고 `skip=`으로 출력한다.** 이게 이 프로젝트의 규율이다
— 측정에서 빠진 게 있으면 반드시 드러낸다. 안 그러면 "n=128을 다 쟀다"는 거짓말이 된다.

❓꼬리질문: "`volatile`을 왜 붙였나?" → `s_act_busy`는 **다른 실행 흐름(로그 태스크)이 바꾸는**
변수다. `volatile`이 없으면 컴파일러가 "이 루프 안에서 아무도 안 바꾸네"라고 판단해서
한 번 읽은 값을 레지스터에 캐시해버릴 수 있다. `volatile`은 "매번 메모리에서 다시 읽어라"는
지시다. (dwt.c:127의 빈 루프와 같은 이유의 다른 얼굴)

### E6. 우선순위 역전 vs 단순 선점 — 면접에서 틀리기 쉬운 지점

`realtime-scheduling.md`에서 공부한 **우선순위 역전**은 이런 상황이다:

> 낮은 우선순위 태스크 L이 자원(뮤텍스)을 잡고 있는데, 높은 우선순위 H가 그 자원을
> 기다린다. 그 사이 중간 우선순위 M이 L을 선점해버리면 → **H가 M보다 낮게 취급되는**
> 역전이 일어난다. (화성 탐사선 Pathfinder 사건이 이것.)

**중요**: 지금 내 구조에서는 우선순위 역전이 **일어나지 않는다.** 뮤텍스를 공유하는 곳이
없기 때문이다 — 큐, 태스크 노티피케이션, 더블버퍼로만 짜여 있고 printf는 로그 태스크
전용이다.

그러니 W3에서 "추론 > 액션"으로 뒤집었을 때 관측되는 건 **단순 선점**이다:
추론이 CPU를 잡고 있어서 액션이 기다리는 것. 이것도 지연이 늘긴 하지만 **역전은 아니다.**

면접에서 "우선순위 역전을 봤습니다"라고 말하면 안 되고, 정확히는:

- "선점으로 인한 지연 증가를 측정했다" (실제로 한 것)
- "우선순위 역전은 뮤텍스 공유가 있어야 발생하는데, 제 구조엔 공유 자원이 없어서
  일부러 만들지 않는 한 관측되지 않는다" (구분해서 말하면 오히려 가점)

❓W3 선택지: 역전을 **진짜 보고 싶다면** 액션과 로그가 뮤텍스 하나를 공유하는 config를
일부러 하나 더 만들면 된다. 그러면 우선순위 상속(priority inheritance)을 켰을 때와 껐을 때의
차이도 잴 수 있다. 시간이 되면 하는 스트레치.

### E7. `xTaskCreateStatic`과 `osThreadNew`는 뭐가 다른가? (app_tasks.c:470)

- **`osThreadNew`** (CubeMX가 만드는 방식): 태스크의 제어블록(TCB)과 스택을 **FreeRTOS 힙에서
  동적으로 할당**한다. 즉 내부적으로 malloc이다.
- **`xTaskCreateStatic`**: 내가 만든 정적 배열을 넘겨준다. 할당이 없다.

우리 규칙이 "malloc 금지"(§S4)인데 태스크 생성이 뒤에서 힙을 쓰면 규칙이 반만 지켜지는
셈이다. 그래서 4개 태스크를 전부 static으로 만들었다. 부수 효과로 **링커 맵에서 메모리
사용량이 전부 보인다** — 실행해봐야 아는 게 아니라 빌드 시점에 확정된다.

CubeMX가 만든 `defaultTask`는 지울 수가 없어서(`.ioc`를 고쳐야 함) `osThreadExit()`로
시작하자마자 종료시킨다.

### E8. 스택 오버플로 훅 — 안 켜면 조용히 죽는다

태스크마다 스택 크기를 내가 정한다(예: infer는 192워드 = 768바이트). **너무 작게 잡으면
스택이 넘쳐서 옆 메모리를 덮어쓴다.** 이게 무서운 이유는 **에러가 안 나고 엉뚱한 변수가
바뀌는** 형태로 나타나서 원인 추적이 거의 불가능하다는 것.

`configCHECK_FOR_STACK_OVERFLOW = 2`(FreeRTOSConfig.h:170)를 켜면 스택 끝에 표식을 깔아두고
태스크 전환마다 검사한다. 걸리면 `vApplicationStackOverflowHook`이 불리고, 우리는 거기서
**LD2를 1초 주기로 느리게 토글**한다 — 정상 동작(50ms 토글, 빠른 깜빡임)과 눈으로 즉시
구분된다.

훅 안에서 printf를 안 부르는 이유: **이미 스택이 깨진 상태**라 더 깊은 함수로 들어가면
남은 정보까지 잃는다.

❓W3에서 실제로 겪을 것: 추론 스텁을 진짜 순전파로 바꾸면 192워드는 부족할 가능성이 높다.
그때 `uxTaskGetStackHighWaterMark()`로 실제 사용량을 재서 맞춘다.

### E9. 플래시할 때 확인할 것 (이 절의 실습)

읽기만 하면 안 남는다. 보드에 올리고 아래를 눈으로 확인하는 게 이 절의 완성이다.

| 확인 | 무엇을 배우는가 |
|---|---|
| LD2가 초당 20번 토글 | E1의 경로가 실제로 도는 것 |
| `[ACT] lat_us med/p99/max` | 컨텍스트 스위치 비용의 실제 크기 |
| `max`가 `med`보다 큰 정도 | 선점·ISR 개입이 만드는 지터 |
| `miss(1ms)=0`, `lost=0` | 마감시한을 지키고 이벤트를 안 놓쳤음 |
| `[SEN] interval_us med` ≈ 10000 | E3의 `vTaskDelayUntil` 수정이 먹혔는가 |
| `win=`이 배치마다 4씩 증가 | hop 64로 윈도우가 쌓이는 중 (2.56초 ÷ 0.64초) |

**추가 실습 (강력 추천)**: `STK_INFER`를 192에서 **32**로 줄이고 플래시해보라.
LD2가 1초 주기로 느리게 깜빡이면 E8의 훅이 잡은 것이다. 증상만 보고 원인을 역추적하는
경험은 코드를 읽어서는 절대 안 생긴다 — 그리고 면접의 "가장 어려웠던 버그" 질문에
쓸 수 있는 건 이런 경험뿐이다.

## S. 시스템 디자인 — 전체 그림

### S1. 최종 아키텍처 (W2 후반~W3에 완성될 모습)

```
[MPU6050] ──I2C 100Hz──> (센서폴링 태스크) ──큐/링버퍼──> (추론 태스크: int8 순전파)
                                                                │ 결과
[타이머 ISR / B1 버튼] ──"마감시한 이벤트"──> (로컬액션 태스크) ──> LED/알림  ← 하드 마감시한
                                                                │
                                  (로깅 태스크: printf 전용, 최저 우선순위) ──> UART
```

지금(W2 2단계)은 이 그림의 **부품 검증 단계**다: main.c에서 스케줄러 시작 전에 DWT selftest → I2C 스캔 → MPU 브링업을 순차 실행하고 있고 (main.c:124-132), 다음 단계가 이걸 태스크 구조로 옮기는 것.

### S2. 왜 태스크 4개로 쪼개나? (수퍼루프 대신 RTOS를 쓰는 이유)

네 가지 일의 **시간 요구가 서로 다르기 때문**이다: 센서폴링은 "정확히 100Hz 주기", 추론은 "무겁지만 급하지 않음(수 ms)", 로컬액션은 "드물지만 발생하면 즉시(하드 마감시한)", 로깅은 "밀려도 됨".

수퍼루프(while(1)에서 순서대로)에서는 추론이 도는 수 ms 동안 액션 이벤트가 와도 추론이 끝날 때까지 기다려야 한다. RTOS는 **선점(preemption)** — 높은 우선순위 태스크가 준비되면 낮은 태스크를 즉시 중단시킴 — 으로 이걸 해결한다. **이 프로젝트의 축 A 실험이 정확히 이 지점의 정량화다**: 추론 태스크의 우선순위/청킹 설정을 바꿔가며 "이벤트→액션 지연 p99·max"가 어떻게 변하는지 잰다.

### S3. printf는 왜 로깅 태스크 전용인가?

printf(UART 115200)는 **느리고 블로킹**이다 — 한 줄에 수 ms. 이걸 센서폴링이나 액션 태스크 안에서 부르면 그 태스크의 타이밍이 printf에 인질로 잡힌다. 그래서 규칙: 급한 태스크는 데이터만 큐에 넣고, 최저 우선순위 로깅 태스크가 한가할 때 찍는다. (브링업 코드가 printf를 직접 쓰는 건 아직 스케줄러 시작 전이라 허용되는 것.)

### S4. 왜 malloc 금지 + 정적 아레나인가?

임베디드 실시간에서 malloc의 세 가지 문제:

1. **비결정성** — 할당에 걸리는 시간이 힙 상태에 따라 달라진다. 마감시한 논의가 불가능해짐.
2. **단편화** — 오래 도는 기기에서 힙이 조각나 어느 날 갑자기 할당이 실패한다.
3. **실패 경로** — NULL 반환을 모든 지점에서 처리해야 하고, 하나라도 빠지면 필드에서 죽는다.

대안: 모든 버퍼를 **컴파일 타임 정적 배열**로 (dwt.c:17, mpu6050.c:21-22 — 이러면 링커 맵에서 메모리 사용량이 전부 보인다), 모델처럼 큰 덩어리는 **아레나**(큰 정적 배열 하나를 앞에서부터 잘라 쓰고, 해제는 통째로만) 방식으로. 차량/가전 펌웨어 코딩 표준(MISRA 등)이 동적 할당을 금지하는 것과 같은 근거 — 이력서의 "결정론적 펌웨어" 한 줄이 이것.

### S5. 왜 int8 추론을 직접 구현하나? (TFLite Micro 안 쓰고)

- **크기/속도**: float32 대비 가중치 메모리 4분의 1. F411은 RAM 128KB라 유의미하다.
- **투명성**: 라이브러리를 쓰면 "왜 이 사이클 수인가"를 설명 못 한다. 직접 짜면 측정 결과 전부가 내 코드 이야기가 된다.
- **서사**: "온디바이스 AI를 갖다 쓴 사람"과 "양자화·메모리 배치를 이해하고 만든 사람"의 차이. 소형 MLP의 순전파는 결국 행렬곱+활성화라 구현 가능한 크기다 (mini-infer에서 PC로 먼저 검증하는 이유).

### S6. "이벤트→액션 지연"이 왜 핵심 지표인가?

스마트홈 엣지 기기의 존재 이유가 "클라우드 왕복 없이 **로컬에서 즉시** 반응"이고, 차량 ECU의 존재 이유가 "**마감시한 안에 반드시** 반응"이다. 두 축의 서사가 이 한 지표에서 만난다. 이벤트를 센서가 아니라 **타이머 ISR/버튼으로 발생**시키는 이유(PLAN.md §1): 발생 시각을 정확히 알아야 지연을 잴 수 있고, 재현 가능해야 하며, 센서 브링업 문제에 측정이 인질 잡히지 않아야 하기 때문.

## Teach-back 하는 법

아무것도 안 지워도 된다. `/clear`도 필요 없고, 지금 대화에서 그냥 하면 된다. 절차:

1. **다은이 먼저 말한다**: 자료 안 보고, 방금 끝낸 단계를 5~10문장으로 Claude에게 설명. ("이번에 MPU6050 브링업을 했는데, 주소가 0x68인 이유는… sleep을 풀어야 했던 이유는…")
2. **Claude가 면접관 역할**: 설명에서 틀리거나 빈 곳을 교정하고, 한 단계 깊은 꼬리질문을 2~3개 던진다.
3. **막힌 질문만** 이 문서(또는 docs/)에서 다시 확인하고, 마지막에 본인 문장으로 3~5줄 요약을 노션에 남긴다.

핵심은 순서다: **자료를 보고 이해했다고 느끼는 것**과 **안 보고 말할 수 있는 것**은 다른 능력이고, 면접에서 쓰이는 건 후자다. 타이밍은 마일스톤 하나 끝날 때마다 15분.

## 면접 대비 — 프로젝트 "밖"에서 놓치면 안 되는 것

위 Q&A는 프로젝트 안의 개념이다. 면접관은 그 경계 바로 바깥을 찌른다.

### 1. 내 프로젝트의 수치를 즉답할 수 있어야 한다

"추론이 몇 사이클이었죠?"에 "음… CSV에 있는데…"는 신뢰가 무너지는 순간이다.
W3~W4가 끝나면 아래를 **외운다** (숫자 5~6개면 된다):

- 추론 1회 사이클 중앙값/p99 (→ ms 환산까지)
- 이벤트→액션 지연 p99: 최악 config vs 최선 config (개선폭이 곧 이력서 문장)
- 모델 크기(KB), 아레나 크기(KB), 전체 RAM/플래시 사용률
- float↔int8 정확도 차이

### 2. 모든 설계 결정에 "대안 + 버린 이유"를 준비한다

면접의 실제 형태는 "왜 X를 썼어요? Y로 하면 안 되나요?"다. 이 프로젝트는 답이 다 있다:

- 왜 RTOS? 베어메탈 수퍼루프로는? → S2 (선점 없이는 마감시한 보장 불가)
- 왜 int8 직접 구현? TFLite Micro는? → S5 + PLAN 변경 이력 (측정 투명성)
- 왜 MLP/작은 모델? 더 큰 모델은? → 측정이 목적, RAM 128KB 제약
- 왜 DWT? 오실로스코프/논리분석기는? → 코어 내장·비침습, 단 외부 관측은 아님
- **PLAN.md의 변경 이력 자체가 무기다**: "처음엔 자율주행 카였는데 이렇게 재설계했다"는
  방향 전환 스토리는 판단력을 보여준다. 전환 이유를 말로 정리해둘 것.

### 3. 삽질 스토리 2~3개를 STAR로 다듬는다

"가장 어려웠던 버그"는 무조건 나온다. 이미 재료가 있다:

- sleep 비트 (통신은 되는데 값이 0 → 배선 의심 → 레지스터 맵 확인 → PWR_MGMT_1)
- HAL 주소 `<<1` (스캔에 아무것도 안 뜸 → 와이어 프로토콜 이해로 해결)
- 포인트: "증상 → 가설 → 검증 순서"로 말하는 것. 결론만 말하면 스토리가 죽는다.

### 4. 임베디드 C 단골 질문 (프로젝트 코드에 이미 다 있다)

- `volatile`의 정확한 의미 — dwt.c:127의 빈 루프, 레지스터 접근. "최적화 방지"보다
  정확하게: "이 메모리는 컴파일러가 모르는 경로로 바뀔 수 있다"
- `static`의 두 용법 — 파일 스코프(s_buf)와 수명. 왜 측정 버퍼가 static인가
- 비트 연산 — `v &= ~MPU6050_PWR1_SLEEP_Msk`를 종이에 쓸 수 있는가
- 2의 보수와 엔디안 — mpu6050.c:108의 `(int16_t)((b[0]<<8)|b[1])`이 왜 음수를 살리는가
- ISR과 태스크가 변수를 공유할 때 생기는 문제(race)와 해법 — W2 후반에 직접 겪을 것

### 5. 내 프로젝트의 한계를 먼저 말할 수 있어야 한다

시니어 면접관에게 가장 강한 신호는 자기 결과물의 한계를 아는 것:

- 데이터는 손 시뮬레이션 proxy다 (실환경 일반화 주장 안 함)
- 측정한 max는 **관측된 최악**이지 보장된 WCET가 아니다 (정적 WCET 분석과의 차이 —
  "그래서 실무에선 마진을 두거나 정적 분석 도구를 쓴다"까지 말하면 만점)
- HSI라 절대 시간 ±1% (사이클 수는 정확)
- n=100의 p99는 사실상 상위 1~2개 값이다 — 꼬리 신뢰도를 높이려면 n을 늘려야 한다

### 6. 지원 도메인별 상식 (깊이 불필요, "존재를 안다" 수준)

- **차량 SW 지원 시**: CAN(차량 내부 버스), AUTOSAR(SW 플랫폼 표준), ISO 26262(기능안전)가
  각각 뭔지 한 문장씩. "이 프로젝트의 마감시한 개념이 기능안전의 어디에 닿는지" 연결만.
- **가전/스마트홈 지원 시**: 왜 클라우드가 아니라 로컬 추론인가(지연·프라이버시·오프라인·비용),
  Matter/Thread 같은 표준의 존재. 이 프로젝트가 "엣지 노드 한 개의 슬라이스"라는 위치 설명.

### 우선순위

1·2·3은 **필수** (프로젝트 발표가 곧 이것), 4는 코드 리뷰형 면접 대비,
5는 꼬리질문 방어이자 차별화 포인트, 6은 서류 낸 회사가 정해진 뒤 반나절.
