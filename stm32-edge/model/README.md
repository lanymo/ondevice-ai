> PLAN.md 110행의

센서 진동 → 통계 특징 → **int8 오토인코더 재구성 오차** → 임계값 → 이상 판정.

## 데이터는 **보드 실측**이다 (2026-08-08 교체)

`accuracy.csv`의 `data_source` 열이 `board_measured`면 실측, `synthetic_proxy`면 합성이다.
이 열은 manifest 파일명으로 자동 판정한다 — 손으로 적으면 갈아끼운 뒤에도 옛 값이 남아
**CSV가 거짓말을 하게 된다.**

### 왜 갈아끼웠나 — 합성 모델은 보드에서 전혀 작동하지 않았다

합성으로 학습한 모델을 보드에 올리자 **정지 상태를 전부 이상으로 판정**했다
(재구성 오차 218,000 vs 임계값 4,294). 특징별로 뜯어보니:

| 원인 | 보드 실측 | 합성이 가정한 값 | z-score |
|---|---|---|---:|
| 장착 기울기 (`ax.mean`) | 2.31° | 0.022° (사실상 완벽 수평) | **+106** |
| 센서 노이즈 (`ax.std`) | 0.0022 g | 0.0160 g (**7.3배 시끄럽다고 가정**) | **-10** |
| 자이로 정지 바이어스 | -7.18 dps | 0.08 dps | **-17** |

입력 양자화 표현범위가 z=±3이었으므로 **24개 특징 중 절반이 int8 끝값에 눌러붙었다.**
흔들어도 값이 더 안 변하니 상대 신호까지 죽는다. **오프셋 보정으로는 못 고친다** —
평균만이 아니라 노이즈의 *크기*가 틀렸기 때문이다. 재수집·재학습이 유일한 길이었다.

> 이건 `synth_data.py`의 버그가 아니라 **합성 데이터의 한계**다. 실제 센서를 본 적 없는
> 생성기는 존재하지 않는 센서를 상상한다. W2에 합성으로 시작한 결정 자체는 옳았고
> (보드 없이 파이프라인 전체를 완성했다), 그 값을 믿은 게 문제였을 뿐이다.

### 실측으로 갈아끼우는 법

펌웨어에 **수집 모드**가 있다 - **B1(파란 버튼)을 누른 채 리셋**하면 세션을 순서대로
안내하며 raw CSV를 UART로 뱉는다 (`firmware/Core/Src/collect.c`). 로그를 넘기면 끝:

```bash
python3 import_board_csv.py ~/w3_collect.log   # -> data/*.csv + manifest.csv
SKIP_SYNTH=1 ./run_all.sh                      # 학습->평가->export->C검증->그래프->펌웨어 동기화
```

임포터가 대신 해주는 것 세 가지 (전부 손으로 하면 틀리는 것들):

1. **환산 상수를 로그 헤더에서 읽는다.** 16384를 코드에 박아두면 나중에 `AFS_SEL`을
   올렸을 때 조용히 4배 틀린 데이터가 만들어진다.
2. **시간축이 끊긴 곳에서 자른다.** I2C 실패 구간은 기록되지 않으므로 파일에서는 붙어
   있어도 실제로는 떨어져 있다. 그 경계를 걸친 윈도우는 없던 급변을 하나 만들고,
   하필 `mad`(인접 차분)가 그걸 특징으로 삼는다 - **배선 사고가 이상 신호로 학습된다.**
3. **라벨 오염을 잡는다.** `normal`이라 적혀 있는데 실제로 움직인 세션을 걸러낸다.
   실측 1차에서 첫 세션이 다른 정상의 **86배**로 흔들려 있었고, 그게 학습셋에 들어갔다면
   오토인코더가 **"흔들림 = 정상"**을 배웠을 것이다 - 정확도 지표는 그럴듯하게 나오면서.

세션을 **여러 개 짧게** 뽑는다 - 이유는 아래 "설계에서 실제로 문제였던 것" §1.

## 파이프라인

```
IMU 100Hz 6축 스트림
   │  윈도우 L=128 (1.28s), hop=64 (50% 오버랩)          features.py
   ▼
24차원 통계 특징   채널 6 × {mean, std, p2p, mad}
   │  z-score (학습셋 통계, 헤더에 같이 구움)
   ▼
int8 양자화        scale/zero_point, CMSIS-NN s8 규약     quantize.py
   ▼
오토인코더 24-12-4-12-24   int8 곱 / int32 누산 / 정수 재양자화   ae_infer.c
   ▼
재구성 오차 err = Σ(q_out - q_in)²      ← **순수 int32, float 환산 없음**
   ▼
err > 4294 이면 이상
```

### 설계 결정 몇 가지

**특징을 왜 24개 통계값으로?** `timeseries-windowing.md` §4의 권고(통계 특징 먼저, 부족하면
raw 1D-CNN). 넷 다 링버퍼 위에서 싸게 계산된다. 표준편차는 **2-pass**로 짰다 — az는 평균 1g에
표준편차 0.005g라 1-pass 공식 `sqrt(E[x²]-E[x]²)`이 float32에서 자릿수를 다 날린다.

**재구성 오차를 왜 정수로?** 출력층의 (scale, zero_point)를 **입력의 것과 같게 강제**했다.
그러면 `Σ(q_out - q_in)²`이 그대로 의미 있는 값이 되어 MCU에서 float를 한 번도 안 쓰고
임계값과 비교할 수 있다 (`anomaly-detection.md` §5).

**재양자화는 CMSIS-NN 규약 그대로.** 정수 곱 + 시프트(gemmlowp `arm_nn_requantize`와 비트정확
동일). 스트레치로 CMSIS-NN 커널을 끼워 넣을 때 drop-in이 되게 하려고.

## 결과 (보드 실측 데이터 기준, 2026-08-08)

정상 231윈도우로 학습(25%는 임계값 산정용 홀드아웃), 평가 181윈도우
(정상 77 / imbalance 38 / impact 38 / looseness 28).

| 모델 | AUC | 정확도 | precision | recall | F1 | FPR |
|---|---|---|---|---|---|---|
| maxabs_z (베이스라인) | 0.9889 | 0.9724 | 1.000 | 0.952 | 0.975 | **0.000** |
| mahalanobis (베이스라인) | 0.9890 | 0.9779 | 1.000 | 0.962 | 0.980 | **0.000** |
| **ae_float32** | **0.9893** | 0.9779 | 1.000 | 0.962 | 0.980 | **0.000** |
| **ae_int8** | **0.9886** | 0.9392 | 0.912 | 0.990 | 0.949 | 0.130 |

이상 종류별 재현율 (int8): imbalance 1.000 / impact 0.974 / looseness 1.000.

### ▶ 양자화 손실: AUC −0.07p, **FPR 0% → 13%**

AUC는 거의 안 떨어지는데 FPR이 튄다. AUC는 순위만 보는 지표라 양자화가 점수를 압축해도
순서가 유지되면 안 변하지만, **임계값 하나로 자르는 순간 압축이 오경보로 나타난다.**
정지 상태의 오차 분포와 임계값 사이 여유가 그만큼 좁아진 것 —
"AUC가 멀쩡하니 양자화 손실은 없다"고 말하면 안 되는 이유의 실례다.

여기에 [kernel_compare.csv](../measurements/kernel_compare.csv)의 결과(**int8이 1.78배 느림**)를
겹치면, 이 규모에서 int8을 쓸 근거는 Flash 0.38% 절약뿐이다.

### ⚠️ 합성 때와 결론이 뒤집힌 곳 — 베이스라인이 거의 따라붙는다

합성 데이터에선 AE가 베이스라인을 크게 이겼다(AUC +1.2~1.5p, FPR 0.24/0.17 → 0.04).
**실측에선 셋이 사실상 같다** (AUC 0.9889 / 0.9890 / 0.9893).

이유는 데이터가 쉬워졌기 때문이다 — 손으로 흔든 이상은 정상 대비 진동이 15~100배라
`maxabs_z`(특징 하나라도 z가 크면 이상) 같은 단순 규칙으로도 갈린다. 합성 데이터가
어려웠던 게 아니라 **어려운 척했던** 것에 가깝다.

**정직한 결론**: *이 데이터셋에서는* AE가 필요 없다. AE의 값어치는 "여러 특징의 **조합**이
정상 범위를 벗어나는" 미묘한 이상에서 나오는데, 그런 이상은 손으로 못 만든다.
AE를 남겨두는 이유는 정확도가 아니라 **온디바이스 int8 추론 파이프라인 자체가 목표물**이기
때문이고, 발표에서도 그렇게 말해야 한다. 덤으로 마할라노비스는 Σ⁻¹이 24×24 = **2.3 KB**라
AE(int8 가중치 672 B)보다 오히려 무겁다.

### ⚠️ 한계 — 장착 각도에 극도로 민감하다 (보드 실측으로 확인)

실측 정상 데이터가 워낙 일관돼서 `ax.mean`의 정규화 std가 **1.9e-4 g**다. 이건
**기울기 0.011°당 z가 1** 움직인다는 뜻이고, 임계 z=3까지 여유가 **0.033°**뿐이다.

데모 중 실제로 관측됐다: 흔들기를 멈춘 뒤에도 이상 판정이 유지됐고, 원인은 보드가
**1.51° 기울어진 것**이었다(z 변화 139). 오작동이 아니라 모델이 "그 각도로 놓인 상태"를
정상으로 배운 결과다.

대응 선택지 (W4 이후):
- `*.mean` 특징 6개를 빼고 `std/p2p/mad`만 쓴다 — 진동 자체는 각도에 무관하다
- 또는 재장착할 때마다 베이스라인을 다시 잡는다 (실제 예지보전 장비의 관행)
- 지금 코드는 전자를 고르면 `config.py`의 `FEATURE_NAMES` 한 줄로 바뀐다

## C 검증 (`cref/`)

`ae_infer.{c,h}` / `ae_infer_f32.{c,h}` / `model_weights.h` / `ae_testvec_board.h`는
`sync_firmware.sh`가 **그대로 CubeIDE 프로젝트로 복사**한다. 그래서 malloc 없음,
libm은 `sqrtf`/`roundf`뿐, HAL/FreeRTOS/CMSIS 의존 없음 — 그 덕에 PC에서 그대로
컴파일해 검증할 수 있다.

`make -C cref test`가 네 가지를 따로 본다:

| 검사 | 기준 | 결과 |
|---|---|---|
| **정수 경로** — Python q_in → q_out, 재구성오차 | **비트정확** | 0/48 불일치 |
| **float 경로** — 특징, z-score | 특징 상대 2e-4 / z 절대 1e-3 | 최대 1.8e-5, 7.4e-4 |
| **end-to-end** — C 자체 경로의 최종 판정 | 판정 뒤집힘 0 | 0/48 |
| **f32 대조군** — float32 순전파 vs Python float64 | atol 1e-4 + rtol 1e-4 | 최대 9.4e-6, 판정 뒤집힘 0/48 |

**왜 f32 대조군까지 검증하나**: 그 커널은 제품 경로가 아니라 속도 비교용이다
(system-design.md §5 — "M4F는 FPU가 있으니 순수 C int8이 더 느릴 수 있다"). 그런데
**검증 안 된 커널이 빠른 건 아무 의미가 없다.** 틀린 커널은 대체로 빠르다.

같은 실행에서 `int8 vs float32 판정 일치 42/48`도 찍힌다 — 양자화가 판정을 실제로
얼마나 바꿨는지의 표본 48개짜리 스냅숏이다(전수는 `accuracy.csv`의 FPR 4.06%→9.28%).

특징·정규화는 Python이 float64, C가 float32라 비트 일치가 애초에 불가능하므로 허용오차로 본다.
정수 경로는 변명의 여지가 없으므로 비트정확을 요구한다.

**z-score를 왜 상대오차가 아니라 절대오차로 보나**: `az.mean`은 평균 0.99968 g, 표준편차
0.00056 g다. `z = (x - 0.99968)/0.00056`의 분자가 큰 수끼리의 뺄셈이라 float32 자릿수가 날아가고,
z가 0 근처인 정상 샘플에서 상대오차가 발산한다(기준 자체가 무의미해진다). z는 이미 표준화된 양이라
절대오차가 옳은 기준이다. 실측 최대 절대오차 7.4e-4 = **양자화 LSB의 0.0102배**로, q_in을
흔드는 0.5 LSB 대비 50배 여유. 테스트가 이 LSB 배수를 매번 찍으므로 여유가 줄면 바로 보인다.

## 설계에서 실제로 문제였던 것 (전부 수치로 잡힌 것들)

### 1. 조건당 파일 하나 → 장착 기울기로 이상을 맞히는 누수

처음엔 조건마다 긴 CSV 하나씩 뽑았다. 그랬더니 **정상** 테스트 세션의 |z| 최대가 26까지 튀고,
imbalance가 `az.mean` 하나로 분리됐다. `az.mean`은 진동이 아니라 **그날의 장착 기울기**다 —
런 단위 nuisance 상수(기울기·자이로 바이어스·회전수)의 산포가 학습셋에 없어서, 모델이
"이상"이 아니라 "다른 세션"을 학습한 것.

→ 조건당 짧은 세션을 여러 개로 바꿨다. 지금은 정상 |z| 최대 5.35, `az.mean`의 이상 종류별
|z|가 0.63~1.59로 평평하다(= 더 이상 신호가 아니다).

### 2. 윈도우 단위 train/val 분할 → 임계값이 너무 빡빡

임계값을 정상 검증셋 p99로 잡는데 FPR이 **25%**(마할라노비스는 39%)가 나왔다. 규칙상 1%여야 한다.
원인: 학습/검증을 윈도우 단위로 섞어 나눠서, 같은 세션 윈도우가 양쪽에 들어가 있었다. 모델이 그
세션의 nuisance 상수를 외워 검증 오차가 낙관적으로 나오고 → 임계값이 과하게 낮게 잡힌 것.

→ **세션 통째로 홀드아웃**으로 바꿨다. FPR 25% → 4.1%. 정규화 통계도 검증 세션을 빼고 뽑는다.

### 3. `in_margin`을 테스트 AUC로 고르고 있었음

입력 양자화 범위 여유를 후보별 **테스트 AUC**로 골랐는데, 이건 하이퍼파라미터 테스트셋 누수다.
"현장엔 고장 데이터가 없다"는 이 프로젝트의 전제와도 모순된다.

→ 라벨을 안 쓰는 기준으로 교체: *표현범위 반폭이 정상 검증셋 최대 |z|의 2배 이상 되는 가장 작은
margin*. 정상은 절대 포화하지 않으면서 이상 쪽에 여유를 남긴다. 같은 값(3.0)이 선택됐고,
`--sweep`으로 찍어보면 1.5~6.0 구간에서 AUC가 평평해 손해 본 것도 없다.

### 4. numpy와 C의 반올림이 다름

`np.round`는 banker's rounding(짝수 쪽), C `roundf`는 0에서 먼 쪽이다. 정확히 .5인 입력에서
q_in이 갈린다. 추론 경로의 반올림이라 Python을 C에 맞췄다(`quantize._round_half_away`).

## 설계에서 실제로 문제였던 것 — 5. 합성 데이터를 믿은 것 (2026-08-08)

앞의 4개는 전부 **PC 안에서** 잡힌 문제였다. 5번은 보드에 올려야만 보였다:
합성 생성기가 가정한 센서(기울기 0.022°, 노이즈 0.016 g)가 **실물과 자릿수가 달랐다**
(2.31°, 0.0022 g). PC 검증은 전부 통과했다 — Python과 C가 일치하는지만 봤으니까.
**"구현이 맞다"와 "모델이 맞다"는 다른 명제**이고, 후자는 실물 없이 확인할 방법이 없다.

교훈은 "합성으로 시작하지 마라"가 아니다. 합성 덕에 보드가 오기 전에 파이프라인을
전부 완성했고, 실측이 들어오자 `manifest.csv`만 바꿔서 그대로 재학습됐다. 교훈은
**합성 단계의 산출물은 "파이프라인"이지 "정확도 수치"가 아니라는 것**이다.
